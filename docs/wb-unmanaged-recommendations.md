# Рекомендации при управлении ставками поиска

`expected_recommendation_bid_kopecks` — необязательное поле политики WB-робота.
Отсутствие поля сохраняет прежний контракт: поиск включён, рекомендации выключены,
ставка рекомендаций у каждого разрешённого SKU равна нулю. Поле не сериализуется
при отсутствии значения, поэтому контрольные суммы существующих политик сохраняются.

Положительное значение, например `153`, разрешает уже включённые рекомендации
только при точном совпадении этой ставки у **каждого** SKU. Проверяются также поиск,
ручной CPC, имя и ID кампании, точный набор SKU без дубликатов. Изменение ставки
рекомендаций, отключение размещения или другой дрейф останавливают наблюдение.

```json
{
  "placement": "search",
  "expected_recommendation_bid_kopecks": 153
}
```

Это фрагмент, а не полная политика. `153` означает 1,53 ₽. Робот отправляет
изменения ставок только в `search`: это поле не разрешает запись в рекомендации
и не меняет размещения кампании. Дневные расходы, лимиты и защитная пауза относятся
ко всей кампании, включая рекомендации. Метрики по размещениям не разделяются
искусственно; отсутствие атрибуции по SKU продолжает блокировать соответствующие
решения. Защитная пауза или отключение SKU применяются ко всей кампании/SKU,
а не только к поисковому трафику.

## Подготовка без включения

Для просмотра нового контракта создайте отдельный файл политики с
`write_enabled=false`, `bid_writes_enabled=false` и ожидаемой ставкой рекомендаций.
Остальные поля скопируйте из действующей политики. Не заменяйте рабочий файл этим
черновиком: подготовка не меняет durable state и не даёт нового разрешения на записи.
Сохраняйте рядом исходную политику и её контрольную сумму для сверки перед переходом.

## Согласованный переход после подготовки

Установка нового кода сама по себе сохраняет старый контракт. Перед включением
нужны отдельное разрешение пользователя, свежая проверка WB и новая активная
авторизация политики. В target-политике разрешено изменить только ожидаемую ставку
рекомендаций и поля авторизации: `authorization_reference`, `authorized_at`,
`observe_until`, `authorization_expires_at`. Срок авторизации не превышает 31 дня.
Смена кабинета, кампании, SKU, автора, коридора, бюджета, DRR, темпа или флагов
записи этим переходом отклоняется.

1. После CI и выпуска установить поддерживающий поле бинарник. Остановить таймер
   конкретной кампании и дождаться завершения её текущего сервиса.
2. Сверить исходную политику и durable digest; проверить отсутствие pending,
   инцидента и всех незавершённых попыток. Не очищать эти поля вручную.
3. После отдельного согласования сформировать target из исходной **live**-политики:
   добавить ожидаемую ставку и новую ссылку/время авторизации; лимиты сохранить.
   Проверить свежие размещения, все ставки, остатки, бюджет и полноту дневных расходов.
4. Выполнить команду ниже. Она имеет только read-token, берёт общую блокировку
   кампании, проверяет WB новым контрактом и полноту дневных расходов, затем меняет
   только digest/revision и добавляет аудит в одной транзакции. Она не запускает
   кампанию и не отправляет ставки или пополнение.

   ```text
   wb-automation authorize-recommendations-pg SOURCE.json TARGET.json ACCESS.json READ_TOKEN false READER_PROXY --confirm-authorized-recommendations
   ```

5. Установить проверенный target атомарно как рабочую политику и сверить digest с БД.
   При неудаче установки оставить таймер остановленным; не возвращать старый digest
   SQL-командой. Несовпадающие файлы и БД блокируют исполнение.
6. Только в пределах отдельного разрешения на включение выполнить первый цикл,
   readback при отправке действия и восстановить таймер. Счётчики, cooldown,
   дневная защитная пауза и история сохраняются.

Повтор команды с уже установленным target идемпотентен, но не обходит инцидент
или pending. Простая замена JSON без перехода не принимается PostgreSQL executor.

Для Nexus и «Одуванчика» подготовленный на 11.10.2026 коридор поиска остаётся
7–12 ₽, пауза — 450 ₽, дневной потолок — 500 ₽, пополнение запрещено. По наблюдению
WB в 12:18 UTC четыре ставки поиска превышали 12 ₽. После будущего включения
обычные циклы могут снизить их до потолка, по одному действию с прежними guards.
Это наблюдение нужно обновить перед включением; оно не является свежим разрешением.

## Исправление ставок выше потолка

После отдельного разрешения оператора можно снизить одну поисковую ставку,
превышающую `max_bid_kopecks`, до этого потолка:

```text
wb-automation explicit-bid-cap-repair-once-pg POLICY.json ACCESS.json READ_TOKEN WRITE_TOKEN LEGACY.json true WRITER_PROXY --confirm-explicit-bid-cap-repair READER_PROXY
```

Команда использует ту же блокировку кампании, PostgreSQL-резервацию, финальное
разрешение на отправку и readback. Она допускает снижение во время cooldown
или паузы; активную кампанию с достигнутым дневным порогом сначала должен
остановить обычный защитный цикл. Ремонт на паузе допускается и при уже
превышенном дневном расходе, поскольку он не возобновляет показы.

Нужны действующая авторизация, полные данные дневного расхода, свободная дневная
квота и отсутствие инцидента или pending. Бюджет, рекомендации и статус кампании
не меняются. Счётчики и защитная пауза сохраняются. При отсутствии превышений
команда ничего не отправляет. После отправки выполните обычный цикл для readback;
не запускайте следующую коррекцию до подтверждения предыдущей. Автоматические
циклы продолжают соблюдать прежние правила cooldown и дневного расхода.
