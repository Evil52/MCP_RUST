# Эксплуатация MCP на Ubuntu

Для передачи проекта используйте [порядок передачи](handover.md), для нового
компьютера — [инструкцию SSH](linux-laptop.md). Реальные адреса, имена
пользователей, правила офисной сети и датированные результаты проверок
хранятся в закрытой эксплуатационной документации.

## Состав системы

Основные компоненты — Rust MCP, Docker, PostgreSQL, сборщики данных и MCP
Tunnel. Аналитический MCP и рекламные исполнители имеют разные полномочия.
Правила Control описаны [отдельно](../ads-control-mcp.md), правила роботов —
в [инструкции WB](../wb-ads-robot-v1.md). Наличие службы или контейнера само
по себе не означает разрешение на её запуск.

## Проверка работающего сервера

После входа проверьте пользователя и имя хоста, затем список служб и таймеров:

```sh
id -un
hostname
systemctl is-active mcp-ozon-base mcp-ozon-collectors mcp-ozon-tunnel
systemctl list-timers --all 'mcp-ozon-*'
curl --fail --noproxy '*' http://127.0.0.1:8787/readyz
```

Эти имена служб и loopback endpoint применимы к соответствующей установленной
конфигурации. Фактические Compose project, контейнеры и пути определяются
по закрытой описи конкретного развёртывания. Не выдавайте Docker или sudo
новому пользователю только ради просмотра состояния.

Успешный readiness проверяйте вместе со свежестью данных и реальным запросом
через MCP. Для роботов нужны завершённые циклы, журнал действий и чтение
статуса кампании у маркетплейса. One-shot служба может быть неактивна между
запусками; это не доказывает неисправность.

## Разработка и production

Рабочая копия разработчика и установленный production release должны
обновляться независимо. Получение Git-ветки не меняет запущенные контейнеры,
секреты, политики, таймеры или рекламу. Перед production-обновлением выполните
[процедуру immutable delivery](../immutable-container-delivery.md) с проверкой
CI, image lock, provenance и доступным откатом.

## Резервные копии

Используйте [инструкцию восстановления](../disaster-recovery.md). Полный
комплект требует согласованной копии БД, артефактов, закрытой конфигурации
и независимо сохранённого ключа расшифрования. Для установок с guard отдельно
проверяется его состояние. Наличие архива не заменяет пробное восстановление
на отдельном стенде. Внешнее хранение и мониторинг копий проверяются отдельно.

## Сеть и доступ к 1С

SSH-ключ разрешает вход только после появления сетевого пути к серверу.
Маршруты, firewall, VPN и доступ к офисным сервисам изменяются отдельно.
VPN отдельной службы не является изоляцией всей Ubuntu или компьютера агента.
Полную изоляцию подтверждают фактические правила и проверки допустимых и
запрещённых соединений, включая сохранение настроек после перезагрузки.

Путь чтения 1С согласуется отдельно. Права только на чтение обеспечиваются
коннектором и учётной записью 1С или БД; firewall ограничивает адреса и порты.
Инвентаризация Hyper-V сама по себе не подтверждает отсутствие записи в 1С.
