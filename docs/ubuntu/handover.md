# Передача MCP новому сотруднику

Передача состоит из исходников Git, закрытых рабочих материалов и отдельно
управляемых доступов. Получение репозитория не устанавливает SSH-ключ,
не переносит секреты и не меняет работающий production.

## Получение исходников

Ветка `handover/ubuntu-transfer-20261020` подготовлена от `origin/master`
на commit `31961be24fb63d48b77e747b8daf49f8e69315e2`. Она содержит актуальный
на момент подготовки код и общие инструкции без закрытой описи инфраструктуры.

На новом компьютере или в отдельной папке разработки Ubuntu:

```sh
git clone --branch handover/ubuntu-transfer-20261020 \
  https://github.com/Evil52/MCP_RUST.git MCP_OZON-handover
cd MCP_OZON-handover
git status --short --branch
git rev-parse HEAD
```

Сверьте HEAD с commit, переданным ответственным за передачу. При наличии
рабочей production-копии не выполняйте в ней pull, reset или checkout ради
этой процедуры. Создайте отдельную копию для ознакомления и разработки.

## Закрытые рабочие материалы

Коммерческие отчёты из `outputs/`, исторические инструкции с реальными
адресами и рабочие доказательства передаются по закрытому каналу. Для этой
передачи подготовлен отдельный локальный архив с пофайловым manifest и
контрольной суммой. Он остаётся на исходном компьютере до фактического
копирования и приёмки. Публичный Git не является его хранилищем.

До распаковки проверьте SHA-256 полученного архива. Распаковывайте его
в новый закрытый каталог, сверяйте содержимое с manifest. Архив сохраняет
доступные локальные материалы; ссылки на отсутствующие временные каталоги
не означают, что их содержимое восстановлено.

Этот архив не является резервной копией production БД или полным disaster
recovery bundle. Действующие `.env`, реестры доступа, политики и ключи
расшифрования остаются в защищённом хранилище. Их состав, актуальность и
доступ преемника проверяются отдельно по [инструкции восстановления](../disaster-recovery.md).
Исторические состояния служб в документах не заменяют свежую проверку сервера.

## Передача SSH и владельцев

Добавьте публичный ключ сотрудника по [инструкции SSH](linux-laptop.md)
и проверьте его вход с собственного компьютера. Зафиксируйте владельцев
репозитория, registry образов, VM, MCP-подключения, резервных копий и
учётных записей маркетплейсов. Личные аккаунты и приватные ключи сотрудников
не передаются как общие пароли.

## Приёмка

- Новый сотрудник входит своим ключом в согласованный серверный аккаунт.
- Получен ожидаемый commit; рабочая копия отделена от production.
- Закрытый архив скопирован, его SHA-256 и manifest проверены.
- Согласованы владельцы сервисов, доступов, бюджета и незавершённых задач.
- Проверены службы, таймеры, свежие циклы сбора и реальный аналитический MCP-запрос.
- Для каждого действующего робота известны политика, лимиты, состояние
  нерешённых действий и способ остановки; статус подтверждён чтением у маркетплейса.
- На отдельном стенде проверено восстановление согласованной резервной копии.

Блокировки `awaiting_readback` и `reconciliation_required` разбираются
через чтение результата, без повторения неопределённой записи.
Для production-обновления требуется отдельная
[процедура релиза и отката](../immutable-container-delivery.md).
После успешной приёмки отзыв прежних доступов и замена соответствующих секретов
выполняются отдельно, сохраняя вход преемника.
