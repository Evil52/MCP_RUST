# Ozon Ads Optimizer: первый контур рекомендаций

`ads-optimizer` читает один подготовленный JSON с данными Ozon CPC и выдаёт
воспроизводимый JSON с рекомендациями по дневным бюджетам SKU. Это **shadow**:
оператор оценивает предложения до любых изменений в рекламном кабинете.
Программа не подключается к Ozon, PostgreSQL или 1С, не загружает `.env` и
конфигурацию из переменных окружения, не запускает Control и не меняет кампании.

Это первый проверяемый этап собственного оптимизатора. Он сопоставляет расходы
с явно выбранной целью: рекламной ДРР **без себестоимости и 1С** либо
ожидаемой экономикой заказа. В обоих режимах ограничены шаг изменения
бюджета и общий бюджет портфеля. Модель не прогнозирует дополнительную прибыль и не измеряет
прирост продаж от рекламы. Достигнутая эффективность XWAY или другая внешняя
результативность этим кодом не подтверждается.

## Запуск

```bash
cargo run --locked --bin ads-optimizer -- --help
cargo run --locked --bin ads-optimizer -- --version
cargo run --locked --bin ads-optimizer -- recommend config/ads-optimizer.example.json
cargo run --locked --bin ads-optimizer -- recommend config/ads-optimizer-drr.example.json
```

В [примере](../config/ads-optimizer.example.json) все данные **SYNTHETIC**:
фиктивный аккаунт, SKU, остатки, наблюдение ограничения по бюджету и экономика. Это воспроизводимая демонстрация
на `2026-09-25T12:00:00Z`, а не выгрузка магазина и не текущая рекомендация.
В [примере без себестоимости](../config/ads-optimizer-drr.example.json)
`economics: null`, цель — рекламная ДРР 15%. Это **демонстрационный**,
а не рекомендуемый для действующих магазинов порог.
Чтобы сохранить результат, оператор сам перенаправляет стандартный вывод:

```bash
cargo run --locked --bin ads-optimizer -- recommend evidence.json > recommendations.json
```

CLI сам не создаёт архивов или других файлов. В stdout при успешном расчёте
попадает только JSON; ошибки уходят в stderr с ненулевым кодом завершения.
Содержимое входного файла и его путь в сообщениях об ошибках не выводятся.
Оператор передаёт обычный неизменяемый на время чтения файл размером не более
4 MiB; директории и символические ссылки отклоняются. Чтение ограничено и
повторно проверяет метаданные файла. Команд исполнения (`apply`, `execute`)
в этом CLI нет.

## Контракт evidence v1

Точные типы определены в [model.rs](../src/reporting/ads_optimizer/model.rs).
Неизвестные поля отклоняются. Денежные поля с суффиксом `_minor` — целые
**копейки RUB**, без плавающей точки. Например, `100000` — 1 000 ₽.
Доли с суффиксом `_bps` — базисные пункты: `1000` — 10%, `2000` — 20%.

| Поле | Смысл и подготовка |
| --- | --- |
| `version`, `marketplace`, `pricing_model`, `currency` | Для этой версии: `1`, `ozon`, `cpc`, `RUB`. Нельзя смешивать CPC с другими моделями оплаты. |
| `objective` | `{"kind":"target_advertising_drr","max_drr_bps":1500}` — рекламная ДРР без экономики, либо `{"kind":"expected_economics"}` — экономика заказа. Отсутствие поля сохраняет прежний режим экономики. |
| `account_id` | Один аккаунт на входной файл. Это идентификатор происхождения данных, а не проверка доступа в кабинете. |
| `source_refs` | Ссылки-идентификаторы на сохранённые выгрузки рекламы, остатков, признаки ограничения по бюджету и выбранную цель. Экономика нужна только в режиме `expected_economics`. Не вставляйте ключи, токены или пароли. CLI сохраняет связь через digest, но сам ссылки не открывает. |
| `as_of` | Зафиксированный момент расчёта UTC. Повторный расчёт того же evidence даёт тот же результат. Для нового операционного запуска готовят новый evidence с актуальным моментом. |
| `observed_at` | Когда рекламные показатели действительно заново получены из исходной системы. Копирование старого файла или чтение старой строки БД не обновляет этот момент. |
| `window_start`, `window_end` | Включительные календарные границы окна. До 90 дней. Календарь исходного отчёта должен последовательно использоваться во всех строках. |
| `coverage_complete` | Подтверждение, что подготовка охватила все необходимые рекламные данные аккаунта и выбранных SKU. Наличие нескольких строк само по себе не доказывает полноту. |
| `products` | До 1 000 уникальных SKU. Для каждого задаются текущий и максимальный дневные бюджеты, дневные данные, остаток, признак ограничения по бюджету. `economics` может быть `null` в режиме рекламной ДРР. |

В `daily` одна строка на дату и SKU, предварительно агрегированная по всем его
CPC-кампаниям без повторного учёта строк. Это портфельный уровень SKU: сами
кампании и распределение бюджета между ними данная версия не моделирует.
Дневной бюджет SKU здесь — **аналитический лимит оператора**. В существующем
[контракте Control](../src/control/policy.rs) у Ozon бюджет относится к кампании
и задаётся на неделю. Поэтому выходную сумму нельзя механически отправить в
API как бюджет кампании, умножить на семь без проверки или использовать как
ставку: сначала требуется согласование стратегии, единиц и распределения SKU
между кампаниями.
Используются `clicks`, `spend_minor`, `direct_orders`, `direct_revenue_minor`.
Показатели должны иметь одинаковые период, аккаунт, SKU и определение прямой
атрибуции. Заказы из другого рекламного среза нельзя добавлять к ним как
независимые продажи.

**Отсутствующая дата — неизвестные данные.** Нулевую строку добавляют только
если источник подтверждает отсутствие активности. Не следует превращать
ошибку загрузки или пропуск отчёта в нули. Повтор SKU или даты считается
ошибкой входного контракта; неполное покрытие отражается в причинах рекомендации.

В `stock` нужны `sellable_units` и собственный `observed_at`. Доступный остаток
проверяется отдельно от свежести рекламы. Отсутствующий, старый или нулевой
остаток не даёт оснований для тестового увеличения расходов.

В `budget_constraint` передают `limited` и `observed_at`: полученное из
источника подтверждение, что текущий бюджет ограничивает рекламу. Его
происхождение фиксируют в `source_refs`. Только свежее `limited: true`
допускает рассмотрение тестового увеличения. Отсутствие, устаревание или
`limited: false` блокируют тестовое увеличение. Возраст проверяется по
`max_data_age_hours`. Заполнить это поле догадкой о низкой ДРР или выгодном CPC
нельзя. Ограничение по бюджету само по себе не доказывает прибыльность новых
расходов: остальные проверки эффективности всё равно обязательны.

### Рекламная ДРР без 1С

Для `objective.kind: target_advertising_drr` достаточно рекламных расходов,
кликов, прямых заказов и атрибутированной выручки, а также актуальных остатков
и бюджетных ограничений. `economics` не требуется и не участвует в расчёте.
Цель `max_drr_bps` задаётся явно: допустимы 1–100 000 bps (0,01–1 000%).
ДРР — отношение расходов к **прямой атрибутированной выручке**, а не к обороту
всего магазина; её снижение не доказывает рост прибыли.

На зрелых данных допустимый расход равен:

```text
выручка × max_drr_bps / 10 000 × (1 − safety_discount_bps / 10 000)
```

Сравнение с фактическим расходом выполняется точно в целых числах, без
предварительного округления среднего CPC. При превышении ориентира
появляется `cpc_above_advertising_drr_ceiling`. В пределах ориентира возможен
ограниченный тест увеличения только при достаточной выборке, свежих остатках
и подтверждённом ограничении по бюджету. Остальные проверки сохраняются.
При отсутствии зрелых заказов выводится `no_mature_orders_for_drr_allowance`:
движок не придумывает стоимость заказа для остановки расходов. Сигнал
нулевых заказов требует отдельного рассмотрения; бюджетные лимиты и проверка
нулевого остатка действуют независимо.

Например, цель 15% и запас 20% дают рабочий ориентир ДРР 12%. В синтетическом
примере зрелая выручка 70 000 ₽ на 1 400 кликов даёт потолок среднего CPC
6 ₽. В отчёте записываются выбранная `objective`, нейтральный
`average_cpc_ceiling_minor` и `cpc_ceiling_basis: target_advertising_drr`.
Поле `economic_average_cpc_ceiling_minor` остаётся `null`, поскольку
экономический предел без затрат не рассчитывался.

### Экономика заказа

Этот раздел применяется только к `objective.kind: expected_economics`.
Для рекламного режима выше подключение 1С не требуется.

`economics.basis` должен быть `expected_per_direct_attributed_order`.
Все его денежные значения относятся к **одному ожидаемому прямому
атрибутированному заказу**, то есть к тому же знаменателю, что и
`daily.direct_orders`. Это не отдельная выкупленная единица и не автоматически
весь оборот из заказов. Оценку согласовывают с риском невыкупа и возврата;
изолированной закупочной цены из 1С для этого недостаточно.

В проверенной оценке нужны:

- `expected_revenue_minor` — ожидаемая выручка с учётом выбранного знаменателя;
- `expected_cost_of_goods_minor` — соответствующая ожидаемая себестоимость;
- `expected_other_costs_minor` — комиссии, эквайринг, логистика, налоги и
  распределённые операционные расходы;
- `return_reserve_minor` — дополнительные потери от возвратов и отмен,
  **ещё не включённые** в предыдущие поля;
- `target_profit_minor` — желаемый остаток прибыли на тот же заказ;
- `source_ref`, `reviewed_at`, `valid_from`, `valid_to` — источник, момент
  проверки и период применимости оценки. Период должен покрывать всё окно
  данных и дату расчёта: `valid_from <= window_start`, `valid_to >= as_of`
  (сравниваются календарные даты).

Во всех частях нужна единая трактовка налогов, количества в заказе, комплектов
и фасовок. Ссылки на источники являются доказательным следом для оператора:
движок проверяет структуру evidence, но не подлинность данных и не качество
вручную согласованных ожиданий.

### Политика

Все пороги указываются явно в `policy`, а не извлекаются из окружения.
Значения примера — демонстрационные настройки, а не рекомендации Ozon
или универсальные параметры для наших товаров.

| Поле | Назначение |
| --- | --- |
| `total_daily_budget_minor` | Общий верхний предел суммы предлагаемых дневных бюджетов. |
| `attribution_lag_days` | Выбранный оператором запас времени на дозревание атрибуции. Это не утверждение об официальном окне Ozon. |
| `min_mature_days`, `min_clicks`, `min_orders` | Минимум зрелых дней, кликов и прямых заказов для положительного сигнала. |
| `max_data_age_hours`, `max_stock_age_hours` | Допустимый возраст рекламного наблюдения и остатков относительно `as_of`. |
| `max_window_end_age_days` | Допустимый возраст последней даты самого performance-окна относительно даты `as_of`, от 1 до 90 дней. В примере — 21 день; порог выбирают с учётом задержки атрибуции. |
| `safety_discount_bps` | Консервативное снижение ориентира выбранной цели. Это запас политики, не статистический доверительный интервал. |
| `max_budget_increase_bps` | Максимальный шаг тестового увеличения текущего дневного бюджета. |
| `budget_decrease_bps` | Шаг предложения сократить бюджет при отрицательном сигнале. |
| `zero_order_spend_allowances` | Только для экономики: порог зрелых расходов без заказов, выраженный в числе допустимых рекламных расходов на заказ. |

## Как читать расчёт

Зрелость определяется по `observed_at` исходных рекламных данных с учётом
задержки атрибуции, **не просто по текущему времени или `as_of`**. Если старый
снимок повторно прочитан через неделю, поздние заказы в нём не появляются.
Свежесть, зрелость и давность периода — отдельные проверки. Заново
загруженное январское окно в сентябре не считается актуальным только потому,
что `observed_at` свежий: если `as_of.date_utc - window_end` превышает
`max_window_end_age_days`, причина `stale_performance_window` блокирует
увеличение и сокращение по результативности. Независимые проверки свежего
нулевого остатка, экономики и бюджетных лимитов сохраняются. Недавние дни исключаются из
эффективностных метрик; общий расход периода остаётся виден в
`all_period_spend_minor`. Точная консервативная граница текущей версии:
`date <= observed_at.date_utc - attribution_lag_days - 1 день`. Например,
при наблюдении 25 сентября и лаге 7 дней зрелыми будут даты по 17 сентября
включительно. Требуется согласование календарных дат исходного отчёта с этой
UTC-границей при подготовке адаптера. Положительные клики без зрелых расходов
или заказы без соответствующей зрелой выручки блокируют решение по
эффективности с причиной `inconsistent_advertising_evidence`; эти данные
требуют проверки, а не автоматической интерпретации нулей как успеха.

В режиме `expected_economics` из ожидаемой выручки вычитаются себестоимость, остальные расходы, резерв
возвратов и целевая прибыль. Положительный остаток —
`advertising_allowance_per_order_minor`, допустимые рекламные расходы на
один заказ при введённых ожиданиях. Когда остатка нет, оснований для
рекламного масштабирования эта экономика не даёт.

Экономический ориентир среднего CPC получается из этого остатка и
исторического отношения зрелых заказов к кликам, с понижающим коэффициентом
политики. Денежный результат округляется вниз до копейки. Это
`economic_average_cpc_ceiling_minor` — **не ставка аукциона**, не прогноз
конверсии и не команда выставить такую ставку. Историческая конверсия не
гарантирует конверсию следующего клика, особенно после роста бюджета.

В синтетическом примере допустимые расходы составляют:

```text
1 000 ₽ − 500 ₽ − 250 ₽ − 50 ₽ − 50 ₽ = 150 ₽ на заказ
150 ₽ × (70 заказов / 1 400 кликов) × 80% = 6 ₽ среднего CPC
```

Исторический средний CPC примера равен 1 ₽. При выполненных проверках
движок предлагает ограниченный тест: дневной бюджет 1 000 ₽ → 1 100 ₽.
Это арифметический результат введённых данных, а не свидетельство реальной
прибыли или ожидаемого прироста заказов. Даже подтверждённое ограничение по
бюджету не даёт величину дополнительной выручки или прибыли: это нужно
отдельно оценить в пилоте.

| `action` | Значение для оператора |
| --- | --- |
| `hold` | Нет основания для тестового увеличения по имеющимся данным; причины требуют прочтения. Это не доказательство оптимальности текущего бюджета. |
| `review_reduction` | Проверить предложение сократить расходы. |
| `review_pause` | Проверить предложение остановить расходы. |
| `test_budget_increase` | Рассмотреть ограниченный тест увеличения бюджета, отслеживая его последующий эффект. |

Всегда читать `action`, `reasons`, `metrics` и `suggested_daily_budget_minor`
вместе. Портфельный предел может дополнительно уменьшить предлагаемые суммы;
он не отменяет причины нехватки данных у отдельных товаров. Данная версия
соблюдает общий денежный лимит, но не ранжирует SKU по ожидаемой добавочной
прибыли. Сначала сохраняются базовые суммы `min(текущий бюджет, предложение
для SKU)`. Если они превышают общий лимит, эти суммы уменьшаются
пропорционально. Иначе оставшийся лимит распределяется пропорционально
ограниченным тестовым увеличениям. При делении целых копеек используются
наибольшие остатки, равенство разрешается по SKU. Неиспользованный остаток
бюджета не обязан быть потрачен.

`input_sha256` идентифицирует нормализованный вход: порядок SKU, дневных строк
и `source_refs` не меняет результат. Это не побайтовая контрольная сумма
исходного файла, электронная подпись, доказательство подлинности или токен
разрешения на действия. Для аудита сохраняют **и evidence, и отчёт**: отчёт
не дублирует все исходные ссылки и значения. Отдельно фиксируют версию binary,
доступную через `--version`.

## Различие рекламных срезов

Опубликованный SKU-снимок использует `expense`, `orders`, `sales`;
`modelOrders` и `modelSales` сохраняются отдельно и не прибавляются к
каноническим KPI. Дневной отчёт кампаний возвращает `moneySpent`, `orders`,
`ordersMoney` и может быть получен в другое время. Без сверки определений
и строк нельзя соединять расход одного отчёта с выручкой другого.

Существующий collector выбирает кампании с `advObjectType=SKU`, но не
фильтрует их по CPC/CPO. Поэтому его общий снимок нельзя автоматически
считать входом CPC-оптимизатора. Адаптер
[`published::CpcCampaignScope`](../src/reporting/ads_optimizer/published.rs)
требует явно подтверждённого списка CPC-кампаний с источником проверки.
Отсутствие 1С не мешает рекламному анализу; согласованность этих данных
остаётся обязательной в обоих режимах.

## Что требуется до пилота на данных магазина

1. Подготовить адаптер к PostgreSQL со сверкой аккаунта, SKU, единиц денег,
   покрытия и определения прямых рекламных заказов. Он должен переносить
   исходный `observed_at`, а не время чтения БД; существующие коллекторы
   нужно отдельно проверить на сохранение такого происхождения.
2. Выбрать цель. Для рекламной ДРР согласовать целевое значение для выбранной
   группы товаров — подключение 1С не нужно. Для режима экономики подготовить
   полный расчёт заказа; [импорт себестоимости 1С](1c-cost-import.md) может
   быть одним из источников, но отдельная закупочная цена его не заменяет.
3. Получить свежие доступные остатки и проверить соответствие SKU комплектам
   и фасовкам. Найти проверяемый источник подтверждения ограничения по бюджету
   и сохранить момент его наблюдения. Определить рабочие пороги для выбранной
   группы товаров.
4. Запускать рекомендации в shadow-режиме на проверенной истории, архивировать
   evidence и результат, сравнивать решения с менеджером. Историческая
   рекламная выручка не заменяет оценку общей маржи после рекламы.
5. Для проверки эффекта организовать ограниченный пилот с сопоставимой группой,
   зрелыми результатами, контролем наличия, цен и сезонности. По результатам
   решать, нужен ли прогноз отклика и распределение бюджета по дополнительной
   прибыли.
6. Только отдельным этапом связать утверждённые действия с
   [Control](ads-control-mcp.md): проверить доступ, действующие параметры
   кампаний, соответствие SKU кампаниям, ограничения изменений и журнал
   результатов. Этот offline CLI такой связи пока не содержит.

Поиск позиции TOP-30, почасовое управление, прогноз отклика и автоматическое
перераспределение бюджета между кампаниями в эту версию не входят.
