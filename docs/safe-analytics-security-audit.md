# Безопасное расширение аналитики: аудит кода

Дата: 2026-09-13. Основа: изолированная ветка от `b2d0acc` и изменения этой
ветки. Это аудит исходного кода и локальных тестов. Рабочие ключи, подписки,
контейнеры, сетевые маршруты и права действующей PostgreSQL здесь не проверялись.
Настройки production не изменялись.

## Реализованный первый шаг

`MCP_DATA_MODE=reporting_only` включает отдельную поверхность MCP для готовой
аналитики. Значение нужно задать в окружении процесса; загрузка соседнего `.env`
в этом режиме отключена. Конфигурация не запрашивает значения ключей Ozon Seller,
Ozon Performance и WB, даже если реестр содержит их имена.

Сервер удаляет клиентские наборы ключей и оставляет в диспетчере только 13
инструментов подготовленной аналитики плюс `marketplace_accounts` и `list_members`.
Вызов прежнего live-инструмента по известному имени отклоняется как `tool not found`.
Позднее подключение WB/Performance-клиента к этому экземпляру не восстанавливает
ключи. Возврата к live-режиму у экземпляра нет.

Сохранены чтение PostgreSQL, проверка кабинета и роли, метаданные отчётов и две
операции постановки локального задания сборщику. Эти две операции правильно
помечены `readOnlyHint=false`: они меняют очередь, а не кабинет маркетплейса.
В каталоге `configured` означает подключённый PostgreSQL-reader; это не доказательство
полноты истории, подписки или полномочий ключа сборщика.

По умолчанию остаётся `live_analytics`; переключение существующего сервера этим
изменением не выполняется. Отсутствие ключей в клиентских объектах дополняет, но не
заменяет отдельную конфигурацию запуска: нельзя передавать процессу legacy `.env`,
секреты маркетплейсов или доступ к их файловому каталогу. В этой ветке предусмотрен отдельный `compose.analytics-reader.yaml`.
Сетевая изоляция и JWKS должны проверяться отдельно для выбранного развёртывания.

Код: `src/config/data_mode.rs`, `src/config.rs`, `src/main.rs`,
`src/server/reporting_mode.rs`, `src/server/router_policy.rs`,
`src/server/tools/directory.rs`.

## Проверенные границы и ограничения

| Требование | Доказательство в коде | Фактический предел |
| --- | --- | --- |
| Личность на каждом HTTP-запросе | `src/http/session.rs::authenticate_request` проверяет JWT до чтения тела и привязывает сессию к subject; `src/auth.rs` проверяет issuer/audience/scopes и реестр | Только JWT-режим подтверждает внешнюю личность. Dev использует локальный `MCP_ACTOR_ID`; наличие режима в коде не доказывает настройку production |
| Кабинет и роль до чтения/очереди | `src/server.rs::resolve_reporting_account`, `resolve_wb_account`, `resolve_store_for_actor`; `src/server/tools/reporting.rs` вызывает проверки до репозитория | Менеджер ограничен своим кабинетом. Финансы и реклама требуют finance/admin; глобальный каталог отчётов и недельный рейтинг требуют admin |
| Изменение доступа без перезапуска MCP | `RegistrySource::load_async`, снимок реестра на один вызов в `OzonMcp::call_tool`; регрессия `reporting_only_rechecks_scope_on_each_read_and_refresh` | Отзыв блокирует следующий запрос данных, статуса и постановку задания. Уже начатый запрос использует согласованный снимок доступа |
| Доступ при исполнении задания | `src/bin/report-collector.rs::run_one_sales_refresh` проверяет кабинет в `collection_plan`; PostgreSQL выдаёт claim с fencing/lease | Запрашивающий сотрудник не перепроверяется при исполнении ранее поставленного задания: claim не возвращает `requested_by`. Сбор разрешён политикой сборщика, загруженной при старте. Не заявляем мгновенную отмену очереди при отзыве сотрудника |
| Только разрешённые HTTP-операции | `src/ozon.rs::post`, `src/wb.rs::request`, `src/wb/policy.rs`, `src/ozon_performance.rs` проверяют точные пути и методы до credentials/network; стандартные домены фиксированы | POST-чтение допустимо; запрещённые изменяющие GET тоже отклоняются. В `reporting_only` live-маршруты вообще отсутствуют. Реальные права ключей вне этих клиентов не ограничены |
| Схемы аргументов | Типизированные `src/server/inputs_*.rs`, `deny_unknown_fields`, проверки дат, размеров, идентификаторов и пагинации | Универсального MCP-инструмента с произвольными host/method/path/headers/SQL нет. Внешняя строка не становится адресом запроса |
| SSRF и перенаправления | Marketplace-клиенты используют `Policy::none()` и `.no_proxy()`; production Ozon URL проверяется в конфигурации; разрешён только явный операторский proxy | Возвращённые площадкой URL сами по себе не загружаются. Новый механизм скачивания потребует самостоятельной проверки URL, IP и каждого перенаправления; текущая защита не является разрешением на произвольный downloader |
| MCP читает подготовленные данные | `ReportingReader`, `src/reporting/mcp_read.rs::verify_runtime_contract`, миграция `019_daily_reporting_mcp_read_views.sql` | Роль `position_reader`, read-only transaction, явные проекции и запрет доступа к базовым таблицам проверяются при подключении. Роль общая для кабинетов; разграничение сотрудников выполняется в Rust, это не отдельный PostgreSQL principal/RLS на сотрудника |
| Отдельный сборщик | `compose.position.yaml`, `compose.reporting-live.yaml`, `collector_service/source_credentials.rs` используют процесс `report-collector`, роль `report_collector` и ограниченную политику кабинетов | Legacy `compose.yaml` всё ещё импортирует `.env` и имеет outbound. Overlay `compose.reporting-reader.yaml` сам по себе ключи и live-инструменты не удаляет; нужен новый режим с отдельной конфигурацией запуска |
| Ограниченная очередь | `src/reporting/refresh_queue.rs`, миграции `023`/`026`: отдельная роль `report_refresh_requester`, request/status-функции, дедупликация, leases, ограничения срока | MCP не может claim/complete или публиковать снимки этой ролью. Это разрешённая локальная запись, не полностью read-only SQL-сеанс |
| Файлы готовых отчётов | `ofk_reports` возвращает ограниченные метаданные; DTO не содержит путей, адресов, provider ID или содержимого файла; `artifact_store.rs` проверяет идентичность/размер/симлинки внутри worker | HTTP/MCP-скачивание артефакта в этой поверхности отсутствует. Поэтому доступ сотрудника при скачивании не проверен и не считается реализованным |
| Секреты, ПДн и недоверенные данные | Очищенные классы ошибок клиентов; `redact_marketplace_pii` для live-ответов; подготовленные типизированные проекции; инструкции о недоверенном содержимом; `src/tool_telemetry.rs` | Маскирование известных полей не доказывает отсутствие всех ПДн в произвольном тексте. Новые источники должны публиковать только необходимые поля. Не включать сырой ответ в ошибки и отчёты |
| Частота, объём, неполные данные | Admission gates/deadlines/ограничение тела в HTTP и marketplace-клиентах; checkpoints, status/pagination_complete в сборщике и снимках | Успешная страница не доказывает полноту. Отсутствующие данные остаются `N/D`; лимиты и объём истории следует проверять для каждого нового финансового метода |
| Журнал обращений | `OzonMcp::call_tool`, `ToolTelemetryService::begin/finish`: actor/tool/account/outcome без аргументов и ответов; при включённом журнале ошибка begin блокирует dispatch | Telemetry опциональна; без её DB-конфигурации durable-журнал не создаётся. Ошибка finish логируется после завершившегося вызова, результат не отменяется |
| Аварийное отключение | Перезагрузка реестра для MCP; отдельные процессы/политика/credential-файлы сборщика | Сборщик держит политику/реестр, прочитанные при старте. Для его немедленного отключения нужен останов процесса или отзыв ключа; редактирование файла само по себе не доказано как моментальный kill switch |

## Что ещё требуется до полной аналитики

1. Для каждого кабинета подтвердить фактическую доступность каждого нужного отчётного
   метода и ограничения подписки. Каталог, имя переменной и тип токена этого не доказывают.
   Более широкие ключи и доступ к площадкам этой веткой не выдавались.
2. Сохранить финансовую детализацию отдельно от агрегированных KPI: не подменять
   оборот начислениями, payout или остатком рекламного бюджета. У нового источника
   должны быть собственные полнота, схема, версия, курсор и доказательство завершения.
3. Для себестоимости существующая модель `unit_economics` и миграция `016` дают основу
   версионируемых внешних фактов, но не подтверждают действующий канал из 1С. Подключать
   отдельную ограниченную выгрузку без доступа сборщика в офисную сеть; такой канал
   в текущем изменении не создан.
4. Перед отдельным запуском `reporting_only` проверить rendered Compose, отсутствие
   marketplace-env/mounts, JWT, допустимый JWKS-канал, отдельные DB-роли и реальные
   запреты сети. Тесты приложения не доказывают политику Docker/Ubuntu.
5. Если требуется именно отзыв полномочий сотрудника при запуске уже созданной задачи,
   расширить контракт очереди actor/account/revision и проверить его перед claim/send.
   Сейчас сборщик исполняет собственную политику разрешённых кабинетов.

## Регрессии и воспроизводимая проверка

Новые тесты используют синтетические реестры/ключи, локальные моки и подставные
репозитории. Production credentials и PostgreSQL не нужны:

```sh
cargo test --lib config::tests::data_mode
cargo test --lib server::tests::analytics_security
```

Проверяются отсутствие lookup всех трёх видов marketplace-ключей, отсутствие
импорта `.env`, отказ при ошибке режима, точный каталог инструментов, отказ live
dispatch, удаление уже подключённых ключей, невозможность повторно прикрепить ключи,
отзыв кабинета между запросами данных/очереди и корректное значение `configured`.

Действующие регрессии дополнительно покрывают отказ записи до credentials/network,
redirect на внутренний адрес, роли финансовых методов, отсутствие ПДн в известных
полях и метаданных отчёта. PostgreSQL-интеграционные проверки привилегий выполняются
только на отдельной одноразовой БД; их прохождение не приписывается текущей production БД.
