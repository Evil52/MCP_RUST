# Общий workflow кампаний WB

Для новой кампании больше не нужны отдельные Rust-модули, SQL-миграции или
скрипт с её ID. Один профиль кабинета задаёт ключи, размещение файлов,
шаблон робота и ограничения ручного управления. Отдельная заявка задаёт
название, товары, начальные ставки, бюджет и срок разрешения.

Сейчас поддерживается WB CPC с ручными ставками в поиске, 1–50 товаров одной
категории. Создание выполняет локальный оператор `wb-automation`; дальнейшие
ручные изменения используют существующие методы Control MCP. Новые методы
создания в HTTP/MCP-реестр этим изменением не добавляются.

## Один раз для кабинета

Подготовить приватный постоянный каталог `/var/lib/wb-campaigns` с подкаталогами
`journal` и `campaigns`, доступный пользователю контейнера UID 10001. Каталоги
должны иметь режим 0700, профиль/заявки/журналы — 0600. Ключи остаются в
отдельных файлах secrets; профиль содержит только пути.

Скопировать и настроить:

- `config/wb-campaign-profile.example.json` → `profile.json`;
- `config/wb-campaign-robot-template.example.json` → `robot-template.json`;
- `config/wb-campaign-fleet.example.json` → `fleet.json`.

В профиле указать существующего администратора кабинета и существующего
независимого approver для Control. Проверяются роли, доступ к кабинету и
seller SID. Шаблон по умолчанию задаёт **700–1200 коп.**, дневной предел 500 ₽,
паузу при 450 ₽, целевой/жёсткий ДРР 15%, отсутствие автопополнения. Срок
разрешения робота берётся из каждой заявки; автоматически он не продлевается.
Служебные ID/name/SKU и старые даты в шаблоне заменяются при подготовке и
никогда не используются для запроса к WB.

Общий контейнер описан в `compose.wb-campaigns.yaml`. Как и существующие
исполнители, он использует проверенные immutable release images и отдельные
read/write egress. Установить его по
[процессу выпуска](immutable-container-delivery.md), задав `WB_CAMPAIGNS_ROOT`,
`WB_AUTOMATION_ACCESS_CONFIG_HOST`, пути к токенам, параметры БД,
`MCP_WB_AUTOMATION_IMAGE` и `MCP_CONTROL_WRITE_EGRESS_IMAGE`. Для каждого
кабинета используется отдельный Compose project и имя egress-контейнера.

Один планировщик запускает каждые пять минут:

```bash
docker compose -f compose.wb-campaigns.yaml run --rm --no-deps wb-campaigns
```

Команда по умолчанию — `execute-fleet-pg /var/lib/wb-campaigns/fleet.json`.
В `fleet.json` перечисляются только явно подключённые кампании. Каждая
использует собственную строку состояния PostgreSQL, блокировку, историю и
квоты. Ошибка одного цикла отражается в результате и не пропускает остальные.
Контроль расхода основан на периодическом чтении: задержка WB или длинный цикл
не дают гарантии остановки ровно в момент достижения порога. Размер списка
должен позволять укладываться в пятиминутный интервал.

## Ключи записи для WB-кабинетов

В общем приватном `.env` предусмотрена отдельная переменная
`<ACCOUNT_ID_UPPERCASE>_PROMOTION_WRITE_TOKEN` для каждого из семи WB-кабинетов.
Существующие `*_WB_API_TOKEN` остаются ключами чтения. Записи в `.env`
перечислены в `.env.example`; новые значения хранятся только в локальном
`.env` с правами 0600. Analytics-сервер получает для writer-переменных пустые
значения благодаря явному переопределению в `compose.yaml` и `compose.canary.yaml`. На Fedora его
Compose-конфигурация также содержит только ключи чтения.

После добавления ключа нужного магазина установить его в отдельный защищённый
файл для робота и Control:

```bash
python3 scripts/install-wb-promotion-token.py --account ip_usovik_wb
```

Установщик проверяет срок, права и совпадение продавца с ключом чтения этого
кабинета, затем создаёт файл `~/.local/share/mcp-ozon-runtime/<account-id>-promotion-write.token` с правами 0600. Существующий
файл с другим ключом не заменяется автоматически. Путь к файлу передаётся как
`WB_AUTOMATION_WRITE_TOKEN_FILE_HOST` в Compose оператора и как
`CONTROL_MCP_WB_PROMOTION_WRITE_TOKEN_FILE_HOST` в отдельный Control кабинета.
Для запуска требуются привязка seller SID в access registry, профиль кабинета
и разрешённая конфигурация исполнителя.

## Для каждой новой кампании

Создать заявку по `config/wb-campaign-request.example.json`. Все ставки —
целые **копейки**, бюджет — целые **рубли**. Указать реальные товары и актуальные
даты. Разрешение запуска действует не более 24 часов; отдельный срок робота
должен покрывать этот период. Положительный бюджет разрешает отдельные шаги
`fund` и `start`; бюджет 0 означает создание без финансирования и запуска.

Следующие команды запускаются бинарником из проверенного выпуска; внутри
Compose они передаются после `run --rm --no-deps wb-campaigns`.

```bash
wb-automation campaign-prepare /var/lib/wb-campaigns/profile.json /var/lib/wb-campaigns/request.json
```

Результат содержит путь `manifest`. Далее использовать именно этот путь:

```bash
wb-automation campaign-launch preflight /PATH/manifest.json
wb-automation campaign-launch create /PATH/manifest.json
wb-automation campaign-launch bids /PATH/manifest.json
wb-automation campaign-export /PATH/manifest.json
```

`preflight` проверяет кабинет, актуальные категории/остатки, пересечения с
другими кампаниями и баланс для разрешённого пополнения. В новом workflow эти
проверки повторяются после ожидания квоты непосредственно перед create.
WB создаёт CPC-кампанию со своей минимальной ставкой; шаг `bids` устанавливает
точные разрешённые начальные ставки и проверяет их независимым чтением.
`export` требует подтверждённых create/bids и создаёт:

| Файл | Назначение |
| --- | --- |
| `robot-policy.json` | Лимиты робота с реальным ID новой кампании |
| `shadow-policy.json` | Политика наблюдения |
| `initial-state.json` | Неизменяемое исходное состояние для первого импорта в БД |
| `control-policy.json` | Проверенная конфигурация ручных ставок, изначально `plan_only` |

Добавить пути `robot-policy.json` и `initial-state.json` в общий `fleet.json`.
Отдельный timer, бинарник и writer для этой кампании не создаются.
Для разрешённого первого запуска:

```bash
wb-automation campaign-launch fund /PATH/manifest.json
# Дождаться двух плановых циклов по новой политике после финансирования.
wb-automation campaign-launch start /PATH/manifest.json
wb-automation campaign-launch reconcile /PATH/manifest.json
```

`fund` переводит один раз точную сумму из заявки, type=1; поддерживается
1–1 000 000 ₽ в пределах дополнительного лимита профиля и правил WB.
`start` проверяет реальные свежие циклы, бюджет, ставки, остатки, отсутствие
расхода/инцидента и блокировку кампании. Отсутствующие данные не считаются
нулевыми. Старый режим Nexus продолжает разрешать только исходные 1000 ₽.

## Дальнейшее управление ставками

Добавить кампанию в общую Control-policy без ручного копирования targets:

```bash
wb-automation campaign-enroll /PATH/manifest.json /PATH/current-control.json /PATH/next-control.json
```

Команда создаёт новый файл, сохраняет существующие кампании/actors/mode,
добавляет точные товары и лимиты, увеличивает revision. Повторное подключение
уже зарегистрированной кампании отклоняется. После установки этой policy и
перезапуска Control используются обычные методы:

1. `wb_promotion_prepare_bid_update` — кабинет, ID кампании и новые ставки;
2. `wb_promotion_approve_bid_plan` — существующий независимый approver;
3. `wb_promotion_apply_bid_plan` — однократная запись и readback;
4. `wb_promotion_bid_plan_status` / `wb_promotion_reconcile_bid_plan` — результат.

Сохраняются JWT, runtime gates, квоты, срок плана и допустимый процент изменения.
Подключение не включает запись автоматически. Выбрать одного владельца ставок:
для ручной сессии исключить кампанию из планировщика робота и проверить отсутствие
незавершённого автоматического запроса. Ручной Control не используется для обхода
инцидента робота. Политику уже работающего робота нельзя менять заменой файла:
состояние БД связано с её digest и требует существующего штатного перехода.

## Повторы и восстановление

Журнал привязан к кабинету и названию, а не к сроку заявки. Общая блокировка
кабинета сериализует операции новых кампаний, включая разные названия с
пересекающимися товарами. Для одного кабинета использовать один постоянный
journal root. Корень с историей должен участвовать в резервном копировании.
Смена заявки, ставки, каталога bundle или версии не снимает старую попытку.

После ошибки create/bids/fund/start выполнить `reconcile`. Он читает WB и
журнал, не повторяет запись и работает при истёкшем разрешении или отозванном
writer. Неизвестный результат остаётся неизвестным. Не удалять журналы для
повтора, не повторять create под другим названием и не пересоздавать seed
вместо восстановления истории. Старые документы Nexus сохраняют прежний
формат сериализации, журнал и узкую процедуру восстановления.

## Проверка реализации

Тесты используют HTTP mock и отдельную тестовую PostgreSQL, без рабочих ключей:

```bash
./scripts/with-position-test-db.sh cargo test --locked -p mcp-ozon --lib control::wb_launch --no-default-features
cargo test --locked -p mcp-ozon --bin wb-automation
cargo clippy --locked -p mcp-ozon --lib --bin wb-automation --tests -- -D warnings
```

Контракт запросов сверялся с
[официальной документацией WB Promotion](https://dev.wildberries.ru/en/docs/openapi/promotion).
