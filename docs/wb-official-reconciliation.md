# WB: сверка двух итогов еженедельного отчёта

Контракт `wb_weekly_primary_totals_v1`, проверен по официальным источникам
13 сентября 2026 года.

| Сводка API | Колонка детализации | Расчёт |
| --- | --- | --- |
| `retailAmountSum` | `retailAmount` | Сумма для `docTypeName=Продажа` минус сумма для `docTypeName=Возврат` |
| `forPaySum` | `forPay` | Сумма для `docTypeName=Продажа` минус сумма для `docTypeName=Возврат` |

[Инструкция WB по еженедельным отчётам](https://seller.wildberries.ru/instructions/ru/ru/material/how-to-read-general-financial-report)
задаёт эти правила для продаж и перечисления за товар. Второй показатель уже
учитывает комиссию и эквайринг, но ещё не все расходы продавца. Доступный
поисковый индекс содержит текст инструкции; прямое открытие страницы во время
проверки возвращало навигационную оболочку.

[Инструкция WB по детализации](https://seller.wildberries.ru/instructions/ru/ru/material/how-to-read-fimancial-reports-detalization)
разделяет тип документа и обоснование операции. Коррекции и компенсации не
дают основания менять тип документа по названию операции. Пустой тип встречается
у услуг. Реализация сохраняет знак самой суммы: отрицательная сумма продажи
уменьшает итог, отрицательная сумма возврата увеличивает его. `abs()` и знак
количества не используются. Это прямое применение указанного правила суммирования.

[Официальная документация WB API](https://dev.wildberries.cn/docs/openapi/documents-and-accounting)
связывает `/sales-reports/list` с таблицей отчётов продавца и показывает точные
строковые денежные поля. Детализация `/detailed/{reportId}` выгружается по
`rrdId` до HTTP 204. Зеркало `.cn` использовано из-за ошибки загрузки `.ru`;
запросы российского сборщика направляются только на разрешённый `.ru`-домен.

Результат `primary_totals_match` означает совпадение ровно этих двух итогов.
`bankPaymentSum`, прибыль, остальные удержания и ежедневные отчёты в эту
версию проверки не входят. В результате перечислены проверенные колонки,
точные суммы и разница «детализация минус сводка» без округления.

Сверка требует одинаковых кабинета, ID отчёта, валюты, периода и дат,
подтверждённой полноты обеих выгрузок, разных наблюдений и хешей источников.
Строки другого отчёта, дубликаты, недопустимые значения и переполнение отвергаются.
Дата `rrDate` не служит фильтром: корректировка принадлежит отчёту по его ID.
Проверка закрытого периода находится у сборщика; переданные функции квитанции
должны происходить из доверенной точки сбора.

Отсутствующее поле означает `unavailable`, даже если предполагается ноль.
Неизвестный или пустой тип документа допустим для данной колонки лишь при
явном нуле; ненулевая сумма с неопределённым знаком делает эту колонку
недоступной для сверки. Регистр, пробелы и похожие названия не нормализуются
в известный тип. Неполные сведения никогда не дают успешный общий статус.

Модуль: `src/reporting/wb_official_reconciliation.rs`. Проверки включают
продажи, возвраты, отрицательные коррекции обоих типов, компенсации,
неизвестные названия, пропуски, разную точность, суммы выше `i64`, чужой кабинет,
дубликаты и неполные выгрузки.

## Сохранение официального отчёта

Миграция `034_wb_official_report_snapshots.sql` создаёт отдельный снимок полного
отчёта. Предыдущий журнал срезов по дате остаётся самостоятельным источником;
строки этих двух источников нельзя складывать как разные операции.
Сохраняются только нормализованные строки, точные денежные колонки, сводка,
два хеша источников, автор публикации и результат двух проверок. Исходный JSON
API, имя продавца и сведения покупателей не сохраняются.

Денежный коэффициент передаётся строкой, хранится точно в диапазоне `i128`
и поддерживает до 18 знаков после запятой. В частности, 16 дробных знаков
`vw` не обрезаются до копеек и не проходят через `f64`. Миграция `035`
расширяет предыдущий журнал `032`, сохраняя его строки, права и исходные хеши.
Повтор старого снимка после смены числового JSON-коэффициента на строковый
распознаётся по точному совпадению нормализованных полей.

Публикация доступна роли `report_collector` через одну ограниченную SQL-функцию.
Она проверяет обе квитанции полноты и их хеши, связывает один кабинет и ID
отчёта, заново вычисляет два итога в PostgreSQL и публикует всё одной транзакцией.
Повтор того же содержимого возвращает исходный снимок. Изменённый отчёт даёт
ошибку ревизии; прежние сведения не перезаписываются. Автор первого снимка
сохраняется и при повторе другим оператором.

`position_reader` и `report_worker` читают только подготовленные представления.
Репозиторий требует кабинет при каждом чтении и ограничивает страницу 1000
строками. Проверка доступа сотрудника остаётся обязательной перед вызовом
репозитория. `published_at` — время публикации снимка; повтор наблюдения из
контрольных точек не означает нового запроса WB. Для проверки изменений
используется новый идентификатор наблюдения.

Четыре проверки на отдельном PostgreSQL подтверждают совпадение расчётов SQL
и Rust, сохранение `unavailable` и расхождений, отказ неполным или подменённым
данным, атомарность, идемпотентность параллельных публикаций, изоляцию кабинетов
при чтении и отсутствие прямых прав записи у прикладных ролей.
