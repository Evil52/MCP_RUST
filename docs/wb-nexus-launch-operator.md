# Разовый запуск Nexus через выделенный WB writer

## Текущая готовность

Кампания Nexus уже создана: ID **40141836** (13 сентября 2026), без бюджета
и запуска. Дальнейшая готовность требует отдельно проверенных runtime artifact,
защитного runner и свежей авторизации; наличие кода ниже не доказывает запуск.
Новая пятёрка
от 13 сентября 2026: 190904855, 207418966, 218972074, 455101276, 529996417 —
ручки мебельные (4263). Она заменяет исходный несовместимый состав из трёх
предметов WB (4263, 6341, 7354). Смена состава не снимает блокировку старой
попытки создания и не заменяет сохранённый манифест. Preflight перечитывает карточки через существующий
reader и требует одну общую категорию до любой записи. Нет доступа к Content
API или неполные карточки — блокер; writer вместо reader не используется.
Состав не заменяется автоматически, разбиение на несколько кампаний также
требует отдельного решения пользователя.

Для новой кампании в статусе 4 WB не предоставляет `/adv/v3/fullstats`
(поддерживаются 7/9/11), но разрешает `GET /adv/v0/start`. Observer в статусе 4
читает состав, ставки, минимумы, бюджет и остатки без fullstats. Оба флага
полноты статистики остаются **false**; это readiness, а не отчёт о нулевом расходе.
Первый `start` требует подтверждений create/bids/fund-response/fund, бюджет
ровно 1000 ₽, два свежих цикла в статусе 4 с тем же бюджетом и политикой,
отсутствие любых прежних actions и циклов в другом/неизвестном статусе.
Под campaign lease проверяются чистое состояние, отсутствие incident/pending/
защитной паузы, текущие ставки и неизменность статуса. Перед GET сохраняется
неудаляемая попытка; ошибка или неизвестный ответ запрещают повторный старт.
Успех подтверждается отдельным чтением active/9, состава, ставок и бюджета.
Для паузы 11 прежние требования полной статистики и двух циклов сохраняются.

Для статусов 4 и 11 перед пополнением должна быть установлена точная
проверенная политика Nexus с действующим разрешением и завершённым окном
наблюдения. Наличие файла политики ещё не доказывает работу runner: два
периодических цикла и состояние PostgreSQL по-прежнему проверяются при `start`.
После active/9 observer использует обычный fullstats; неполные данные не дают
права менять ставки. Дневной лимит контролируется по доступной статистике WB,
а не является гарантией отсутствия перерасхода при задержках API. Первый
старт сам по себе не доказывает успешный последующий цикл робота.
Статус кампании перечитывается в write guard; установленная политика повторно
проверяется после последнего чтения баланса, до создания `fund-attempted.json`.

Источники: [правило одной категории](https://seller.wildberries.ru/instructions/ru/am/material/how-to-start-and-edit-promotion-campaigns?recommended=true),
[контракт статистики WB](https://dev.wildberries.ru/openapi//promotion).

Это локальный operator CLI в существующем `wb-automation`, **не** финансовый
инструмент аналитического MCP. Он ограничен `ofk_region_wb`, названием `Nexus`,
пятью согласованными nm_id и одним переводом **1000 ₽ / type=1**.

Контракт проверен по [документации WB](https://dev.wildberries.ru/openapi/promotion):
`POST /adv/v2/seacat/save-ad`, `PATCH /api/advert/v1/bids`,
`POST /adv/v1/budget/deposit?id=...`, `GET /adv/v0/start?id=...`.
Ставки — в копейках, сумма deposit — в рублях. `type=1` — «Баланс» WB
(взаиморасчёты из продаж); это не `type=0` «Счёт» и не бонусы `type=3`.
Полей cashback в запросе нет. Внешние платежи и автопополнение не реализованы.
В ответе GET баланса источник **type=1 читается из `net`**. Поле `balance`
означает предварительно пополненный счёт (type=0); бонусы — отдельный источник.
Нет `net`, значение null/некорректно — блокировка, без подстановки других полей.
Это доступность взаимозачёта для рекламы, не сумма к выводу из магазина.
Соответствие полей и рублей также определено в
[контракте тестового баланса WB](https://dev.wildberries.ru/ru/openapi-other/sandbox-environment).

## До исполнения

1. Для текущего продолжения пользователь подтвердил 922 коп. для каждого
   из пяти товаров Nexus. Для иной кампании или состава получить отдельные
   точные ставки: значения в примере сами по себе не являются разрешением.
2. Проверить сборку, тесты и runtime artifact обычным процессом проекта.
   Наличие кода в checkout не обновляет production и не запускает кампанию.
3. Подготовить приватный JSON-манифест (0600) и устойчивый каталог журнала
   (0700). Один и тот же каталог должен монтироваться во все operator-запуски.
   Не использовать `/tmp` для журнала реальных финансовых операций.
4. Использовать существующие account-bound reader/writer credentials и
   изолированные egress proxies. Writer должен быть Personal production,
   promotion-only read/write, с тем же seller SID, что и reviewed registry.
   Не расширять allowlist без отдельного разрешения и не использовать аналитический токен для записи.

Reader-маршрут для проверки категорий должен разрешать точный
`content-api.wildberries.ru:443`. В версионируемой конфигурации reader-прокси
этот домен добавлен; writer allowlist остаётся только Promotion API.
CONNECT-прокси не проверяет HTTP-методы внутри TLS: режим read-only обеспечивает
обязательная проверка reader-токена и фиксированные методы клиента. Нет wildcard,
перехвата TLS, логирования токенов или публикации порта на хост.
До общего релиза допустим отдельно разрешённый временный экземпляр штатного
reader-прокси в собственной internal-сети; он удаляется после проверки и
не заменяет работающие общие прокси. Само изменение файла не обновляет production.

Манифест содержит следующие поля; пути примерные, токены сюда не вставляются:

  "source_policy_sha256": "SHA256_OF_CANONICAL_RUST_SERIALIZED_POLICY",
  "bids_kopecks": {
    "190904855": 922,
    "207418966": 922,
    "218972074": 922,
    "455101276": 922,
    "529996417": 922
  },
  "budget_rubles": 1000,
  "funding_type": 1,
  "actor_id": "rustam_magasumov",
  "authorization_reference": "REPLACE_WITH_EXACT_USER_AUTHORIZATION",

Для финансовых команд требуется admin в локальном reviewed access registry.

## Команды

### Продолжение подтверждённого создания Nexus

Для уже подтверждённой кампании **40141836** предусмотрена отдельная
авторизация `continue_created`, а не изменение `recreate-manifest.json`.
Её узкий состав: `ofk_region_wb`, Nexus, указанная пятёрка, по **922 коп.**
на каждый товар, ровно **1000 ₽ / type=1**, `scope: fund_and_start`,
без `recreate`. Другие ID, ставки, сумма или источник не допускаются.
Время/ссылка разрешения должны быть новыми, после успешной попытки создания;
срок действия по-прежнему не более 24 часов.

В новый манифест добавляются:

```json
{
  "continue_created": {
    "campaign_id": 40141836,
    "previous_manifest_sha256": "HASH_OF_RECREATE_MANIFEST",
    "previous_attempt_sha256": "HASH_OF_RECREATE_CREATE_ATTEMPTED",
    "previous_receipt_sha256": "HASH_OF_RECREATE_CREATE_RECEIPT",
    "previous_policy_sha256": "HASH_OF_RECREATE_POLICY_RECEIPT"
  }
}
```

Хеши вычисляются из разобранного JSON через `serde_json::to_vec(Value)`.
Четыре файла остаются неизменными. Проверяется и цепочка первоначальной
неуспешной попытки. Старые попытки ставок/пополнения/старта, даже повреждённые
или неполные, запрещают переход. Нельзя создать новый каталог журнала,
подменить ID или скопировать receipts вместо этой проверки.

```sh
wb-automation campaign-launch preflight /etc/wb-automation/nexus-continue.json
wb-automation campaign-launch prepare /etc/wb-automation/nexus-continue.json
wb-automation campaign-launch bids /etc/wb-automation/nexus-continue.json
# Установить отдельного Nexus runner по проверенному release/guarded workflow.
wb-automation campaign-launch fund /etc/wb-automation/nexus-continue.json
# Проверить два периодических ready-state цикла; затем:
wb-automation campaign-launch start /etc/wb-automation/nexus-continue.json
wb-automation campaign-launch reconcile /etc/wb-automation/nexus-continue.json
```

`prepare` не отправляет торговых запросов: выполняет fresh preflight,
проверяет статус 4/бюджет 0/минимумы и сохраняет `continue-policy-receipt.json`.
Этот receipt ещё **не установленный робот**. Сохраняются cap 500 ₽, stop 450 ₽,
целевой и жёсткий ДРР 15%, диапазон 500–1050 коп., cooldown 1800 секунд,
отключённое автопополнение и остальные настройки проверенной source policy.
Перед PATCH ставок для продолжения повторяется полный preflight.

Авторизация и дальнейшие этапы добавляются как `continue-*.json` в тот же
устойчивый каталог под тем же OS-lock. После регистрации старые write-манифесты
заблокированы; их read-only reconcile остаётся доступным. Создание через новую
авторизацию запрещено. Повторный `prepare` только проверяет тот же receipt,
не перезаписывает его и запрещён после начала торговых стадий.
Истечение/изменение разрешения не даёт второй денежной попытки.
Наличие attempt, response или receipt закрывает повтор даже после перезапуска.
При неизвестном результате остаётся только readback/reconcile.

Первый старт использует настоящий прежний `recreate-create-receipt.json`,
а ставки/пополнение/старт — новые `continue-*` записи; фиктивный create/fund
receipt не создаётся. Все существующие проверки budget, writer, egress,
installed policy, PostgreSQL lease, двух циклов и incident/pending остаются.
После старта обязательны независимый WB readback и следующий цикл робота.

### Явно разрешённая замена прежней попытки создания

Для новой пятёрки доступна одна отдельная ревизия создания, только `create_only`
и бюджет 0. В свежий манифест добавляется `recreate` с двумя SHA-256:
`previous_manifest_sha256` и `previous_attempt_sha256`. Хешируются разобранные
JSON старых `manifest.json` и `create-attempted.json`, сериализованные через
`serde_json::to_vec(Value)`; это не хеш исходного форматирования файла.

Новое разрешение должно отличаться от старого и быть выдано после его
истечения и прежней попытки. Допустим только исходный старый состав Nexus,
без подтверждённого ID и любых свидетельств дальнейших этапов. Повторная
попытка проверяет имена всех современных WB кампаний типов 8/9, включая
завершённые, с проверкой полноты общего списка (максимум 500), а не только активных.
Только завершённые/удалённые/отклонённые кампании устаревших типов 4–7
не запрашиваются в v2 details: они не могут быть результатом текущего CPC create,
и WB исключил их из API подробностей ([объявление WB](https://dev.wildberries.ru/forum/1659)).
Их ID, счётчики и дубли всё равно проверяются в общем списке. Неизвестный тип,
статус, действующая устаревшая кампания или неполные детали современных кампаний
блокируют POST. В preflight сохраняются общий и фактически проверенный счётчики.

В прежнем каталоге под тем же OS-lock добавляются `recreate-manifest.json`,
`recreate-create-attempted.json` и последующие `recreate-*-receipt.json`.
Ни один старый файл не удаляется или перезаписывается. Для этой ревизии
разрешён максимум один новый POST создания; ошибка, таймаут или повреждённый
attempt снова оставляют только reconcile. Третья ревизия не поддерживается.
После регистрации ревизии старые write-команды закрыты. `fund` и `start`
запрещены и манифестом, и журналом ревизии; это не разрешение расходования.
Команды остаются `campaign-launch preflight/create/bids/reconcile` с новым
манифестом. Проверка без записи не меняет старый журнал; реальные команды
нельзя выполнять до проверки сборки и свежих account-bound предусловий.

Для нового разрешения **только создать, пользователь пополняет сам** задайте
`scope: "create_only"` и `budget_rubles: 0`. Такой манифест разрешает только
`preflight/create/bids/reconcile`, не запрашивает баланс и запрещает `fund/start`
до любых записей. Это не отключает защитные проверки финансового сценария:
он остаётся отдельным разрешением `fund_and_start` на ровно 1000 ₽.

Внутри штатного изолированного runtime с устойчивым журналом:

```sh
wb-automation campaign-launch preflight /etc/wb-automation/nexus-launch.json
wb-automation campaign-launch create /etc/wb-automation/nexus-launch.json
wb-automation campaign-launch bids /etc/wb-automation/nexus-launch.json
wb-automation campaign-launch fund /etc/wb-automation/nexus-launch.json
wb-automation campaign-launch reconcile /etc/wb-automation/nexus-launch.json
```

`preflight` ничего не записывает. Для повторного создания сначала проверяет
неизменность разрешения и отсутствие новой попытки в локальном журнале;
занятая попытка блокируется до обращения к WB. Затем читает WB: source campaign, пересечения с незавершёнными
кампаниями, текущие категории точных SKU, запас WB не менее 20 шт. по каждому
SKU; доступный баланс взаимозачёта `net` читается только для `fund_and_start`.
`create` оставляет кампанию в статусе 4/11 и сохраняет подтверждённый ID.
`bids` проверяет минимумы WB и перечитывает точные ставки.
`fund` заново проверяет состояние, требует бюджет 0 ₽, выполняет один
POST и подтверждает `total=1000` ответом WB и отдельным GET бюджета.
Команда допускает status 4/11, но не устанавливает робота автоматически.
Его проверенная политика должна существовать **до** `fund`.

Все write-стадии сохраняют `*-attempted.json` через `create_new`, `fsync(file)`
и `fsync(directory)` **до** сетевого запроса. Повтор этапа запрещён даже при
ошибке HTTP, таймауте, падении процесса или частичной записи журнала.
Одновременное исполнение исключает OS file lock. `reconcile` не пишет ни WB,
ни журнал и доступен после истечения авторизации. При неизвестном ID после
create требуется сверка списка кампаний; автоматического повторного create нет.

## Защитный робот и старт

Из `policy-receipt.json` (для продолжения — `continue-policy-receipt.json`)
устанавливается отдельная политика **Nexus**; все
торговые защитные параметры копируются из проверенной текущей политики
«Одуванчика»: cap 500 ₽, pause 450 ₽, target ДРР 15%, autotopup off и остальные
пороговые настройки без ослабления. Исходный робот не меняется.

Установить отдельный периодический runner обычным immutable-release процессом
проекта, seed/activate PostgreSQL state обычным guarded workflow. Этот CLI
не устанавливает LaunchAgent, не импортирует/обнуляет состояние робота и не
снимает incident locks. До старта нужны **два** записанных в PostgreSQL цикла
с интервалом 240–420 секунд; последний не старше 90 секунд.

```sh
wb-automation campaign-launch start /etc/wb-automation/nexus-launch.json
wb-automation campaign-launch reconcile /etc/wb-automation/nexus-launch.json
```

Для `start` требуется существующий `WB_AUTOMATION_DATABASE_URL`, точная
установленная политика, campaign advisory lease, отсутствие pending/incident/
protective pause, свежий полный guard snapshot, бюджет 1000 ₽ и нулевой расход.
Для новой кампании в статусе 4 применяется описанный выше provenance-путь:
полнота fullstats остаётся false, а безопасность подтверждается receipts и
двумя ready-state циклами. Для статуса 11 неполная статистика блокирует старт.
Ни в одном случае отсутствие данных не подменяется нулями.

После HTTP start статус 9, товары и ставки проверяются независимо. Затем
обязательно проверить **следующий** реальный периодический цикл Nexus:
сам факт start/readback не является подтверждением работы робота после старта.

## Границы первого rollout

Реальная кампания/перевод не выполняются тестами. Для production нужны
подтверждённые начальные ставки, отдельный установленный runner и проверенный
runtime artifact. CLI не добавляет широких финансовых полномочий MCP и не
может пополнять существующий «Одуванчик», другие кабинеты или другие кампании.
