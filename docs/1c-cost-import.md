# Подготовленная выгрузка себестоимости из 1С

Этот этап добавляет контракт JSON и атомарное сохранение себестоимости в
PostgreSQL. Реальная 1С ещё не подключена. Модуль не знает адресов офисной
сети, не открывает HTTP-сервер и не обращается к 1С, Windows Server или SQL.
Выгрузка и сопоставление номенклатуры с SKU выполняются на стороне учётной
системы; подготовленный файл передаётся оператору или выделенному процессу
импорта. Учётные данные маркетплейсов ему не нужны.

## Контракт JSON v1

```json
{
  "version": 1,
  "account_id": "ozon_store",
  "marketplace": "ozon",
  "source_id": "one_c_main",
  "export_id": "costs_20260913_001",
  "exported_at": "2026-09-13T10:00:00Z",
  "rows": [
    {
      "source_row_id": "line_1",
      "sku": 3411079879,
      "amount_minor": 12345,
      "currency": "RUB",
      "allocation": "per_unit",
      "vat_treatment": "included",
      "vat_rate_bps": 2000,
      "effective_from": "2026-09-01",
      "effective_to": "2026-09-30"
    }
  ]
}
```

- Максимум 4 МиБ и 10 000 строк. Пустой пакет, неизвестные поля, повторённые
  ключи JSON, неизвестная версия и некорректные значения отвергаются целиком.
- `account_id`, `source_id`, `export_id`, `source_row_id` — ASCII-идентификаторы
  из букв, цифр, `_`, `-`, от 1 до 128 байт. Строка источника уникальна в пакете.
- `marketplace`: `ozon` или `wildberries`. SKU — положительный идентификатор
  площадки, помещающийся в PostgreSQL `bigint`; для WB используется nmID.
  Внутренний код номенклатуры 1С нельзя автоматически трактовать как SKU.
- `amount_minor` — целое неотрицательное число копеек за одну единицу товара.
  `12345` означает 123,45 ₽. Дробные числа, строки с суммой, отрицательные
  значения, другая валюта и другое распределение затрат не поддерживаются.
  Ноль допустим только как явно переданная нулевая себестоимость.
- `vat_treatment`: `included`, `excluded`, `not_applicable`. Первые два требуют
  явного `vat_rate_bps` от 0 до 10 000; например, 2000 означает 20%.
  `not_applicable` требует `null`. Это описание полученной суммы, а не вывод
  о действующей ставке налога или праве на вычет. НДС автоматически не
  пересчитывается. Прибыль нельзя считать, смешав суммы с разной налоговой базой.
- Обе границы периода обязательны и включаются в период. Допустимы даты
  2000–2200; начало не позже конца. Бессрочные значения не поддерживаются,
  чтобы следующий импорт не требовал скрытого изменения прежней строки.

## Область доступа и сохранение

`CostImportScope` создаётся только из доверенной конфигурации сервера:
разрешённый кабинет, площадка, источник и конечный список SKU. Нельзя
сформировать разрешения из самого импортируемого файла. Импорт вне этой
области отклоняется до подключения к БД. Бинарник `cost-import` проверяет
роль finance/admin и доступ сотрудника к кабинету по текущему реестру.

`ValidatedCostBatch::parse_json` проверяет весь пакет, упорядочивает строки и
считает SHA-256 канонического содержимого. Изменение пробелов и порядка строк
не меняет идентичность. Повтор того же `export_id` с тем же содержимым
возвращает прежнюю квитанцию; изменение содержимого под этим идентификатором
даёт конфликт. Это проверка целостности и идемпотентности, не цифровая подпись
1С и не доказательство правильности переданной себестоимости.

`PostgresCostRepository::import` записывает пакет одной транзакцией. Любая
ошибка строки откатывает весь пакет. Квитанция содержит идентификатор пакета,
кабинет, источник, идентификатор выгрузки, SHA-256, число строк, серверное время
приёма, `imported_by` и признак повтора. `imported_by` — ограниченный ASCII-ID
сотрудника из доверенного реестра, переданный после авторизации через
`CostImportScope`; имя, почта и другие персональные поля не копируются.
Поле сохраняется в неизменяемом пакете PostgreSQL. Экспорт не может задать
`imported_by`: такое неизвестное поле отклоняется. Идентификатор сотрудника не
входит в хеш содержимого выгрузки: повтор от другого разрешённого сотрудника
возвращает исходный пакет и первоначального автора импорта. В квитанцию и
ошибки не попадает исходный JSON.

Миграция `033_1c_cost_import.sql` создаёт отдельные таблицы
`daily_reporting.cost_import_batches` и `cost_import_entries` и роль
`report_cost_importer`. Роль по умолчанию `NOLOGIN`: миграция не устанавливает
пароль и не включает импорт. Активация и передача отдельного секрета БД
потребуют отдельного развёртывания. Роль получает только чтение и добавление
в новые таблицы, без `UPDATE`, `DELETE`, `TRUNCATE`, изменения схемы и прав на
таблицы маркетплейсов. Серверное время и транзакцию приёма подменить через её
колоночные права нельзя. После фиксации транзакции пакет закрыт для новых строк.

Ограничение GiST, использующее стандартное расширение PostgreSQL `btree_gist`,
запрещает пересечение периодов одного кабинета, площадки и SKU, в том числе
при конкурентной записи и смене источника. Соседние периоды допустимы:
01–30 сентября и 01–31 октября. Исправления прежней себестоимости пока
отклоняются; версия с явным аннулированием и пересчётом отчётов требует
отдельного контракта. Старая таблица `unit_economics_inputs` не перезаписывается
и не объединяется с новой историей автоматически.

## Чтение и неполнота

`report_worker` получает только SELECT новых таблиц; у `report_collector`,
`position_reader` и `report_refresh_requester` доступа к ним нет. Модель не
получает импортирующий инструмент. Чтение через `lookup` всегда ограничено
доверенной областью доступа, SKU, датой действия и моментом знания отчёта:
строка с более поздним временем приёма не включается в старый срез.
Для строго воспроизводимого готового отчёта нужно дополнительно закрепить
выбранные идентификаторы пакетов или отсутствие себестоимости в его манифесте:
одного времени недостаточно, если конкурентный импорт начался до среза,
а зафиксировался после чтения отчёта.

Отсутствующая себестоимость возвращается как `None` / `N/D`, не ноль.
Соединение с финансовым журналом, налогообложением, возвратами, распределением
накладных расходов и окончательной прибылью должно отдельно проверять
совместимость периодов и базы сумм. Наличие импортированной строки само по
себе не подтверждает полноту расчёта прибыли.

## Проверка без продакшена

Unit-тесты проверяют точные суммы, НДС, неизвестные поля, границы, область
доступа, пересечения и каноническую идентичность. `cost_import_postgres`
проверяет отдельную роль, отказ записи чужими ролями, идемпотентность,
атомарный откат, конкурирующие периоды, закрытый пакет, чтение по кабинету
и исторический момент знания. Интеграционный тест активирует роль только в
одноразовой тестовой БД из `scripts/with-position-test-db.sh` и пропускается
без тестовых переменных подключения. Боевые ключи и БД для него не нужны.

## Операторский CLI

Бинарный файл `cost-import` принимает только подготовленный локальный файл:

```sh
cost-import validate /srv/cost-import/incoming/costs.json
cost-import import /srv/cost-import/incoming/costs.json
```

`validate` проверяет контракт и текущие права сотрудника и выводит SHA-256,
идентификатор выгрузки и число строк; к БД он не подключается. `import`
дополнительно требует включённую политику и отдельную роль БД, повторно
проверяет политику и реестр непосредственно перед импортом и выводит квитанцию.

Конфигурация передаётся сервисом через окружение; `.env` автоматически
не читается:

| Переменная | Назначение |
| --- | --- |
| `COST_IMPORT_POLICY` | Путь к отдельной доверенной политике JSON |
| `MCP_ACCESS_CONFIG` | Путь к существующему реестру кабинетов и сотрудников |
| `COST_IMPORT_ACTOR_ID` | Зарегистрированный локальный оператор роли `finance` или `admin` с доступом к кабинету |
| `COST_IMPORT_DATABASE_URL` | Только для `import`: отдельное TCP-подключение с паролем роли `report_cost_importer`; секрет не включают в командную строку или примеры |

Стартовый пример — `config/cost-import-policy.example.json`:

```json
{
  "version": 1,
  "enabled": false,
  "account_id": "ozon_store",
  "marketplace": "ozon",
  "source_id": "one_c_main",
  "allowed_skus": [3411079879]
}
```

Пример не включает импорт. Кабинет и конечный список SKU должен задать
оператор независимо от выгрузки; сам файл не назначает пользователя или права.
Политика и реестр должны находиться в управляемых оператором каталогах;
их нельзя делать доступными для записи другим пользователям.

CLI отвергает символические ссылки, несколько жёстких ссылок, файлы
с превышением размера, права групповой/общей записи у политики и реестра.
Метаданные сравниваются до открытия, у открытого дескриптора и после чтения;
замена inode или изменение размера/времени отвергаются. Чтение ограничено
по числу байт. Это дополнительная проверка файлов, а не песочница для каталога,
которым управляет враждебный процесс. Подготовленная выгрузка может быть
доступна на чтение, но не должна содержать ключи, контакты покупателей и
непредусмотренные поля.
