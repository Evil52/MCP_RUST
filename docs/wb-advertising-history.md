# История рекламы Wildberries

Общий механизм для любого WB `account_id` из реестра. Привязки к ИП Усовик,
названиям или ID кампаний в коде нет. MCP создаёт локальное задание; отдельный
сборщик читает Promotion API. Ставки, запуск, бюджет и пополнения не меняются.

## MCP

Доступ: `finance`/`admin`, только к кабинетам, разрешённым текущим реестром.
Все три команды доступны также в `reporting_only`, где нет ключей WB.

```json
{"tool":"wb_advertising_history_sync","arguments":{"account":"ip_usovik_wb"}}
{"tool":"wb_advertising_history_status","arguments":{"account":"ip_usovik_wb"}}
{"tool":"wb_advertising_history_stats","arguments":{"account":"ip_usovik_wb","group_by":"campaign","limit":100}}
```

Для другого магазина меняется только `account`. Для выбранного периода задайте
`date_from`/`date_to` в `YYYY-MM-DD` (конец включительно). Без дат статистика
охватывает доступный архив. Поддерживаются группировки `campaign`, `day`, `sku`.
`totals` всегда относится ко всему периоду, независимо от страницы `rows`.
Следующую страницу запрашивают с возвращённым `next_offset`.

`sync` без начала периода сначала получает полный доступный список кампаний,
затем в отдельных сохранённых заданиях читает даты создания неизвестных кампаний.
Используется `timestamps.created`, а не `changeTime` списка и не дата последнего
запуска. Если создание неизвестно, история собирается с консервативной границы
2010-01-01, что явно отражается в `unknown_creation_dates`.

Одновременные одинаковые запросы объединяются. Повтор после завершения создаёт
новую загрузку: это позволяет получить поздние конверсии и исправления WB.
`status` показывает последнее задание, количество выполненных запросов,
`requests_with_gaps`, класс ошибки и время следующей попытки. Ответ `sync`
содержит именно принятое/объединённое задание.

## Расчёт и полнота

ДРР = сумма рекламных расходов / сумма приписанных рекламе заказов × 100.
Это сумма заказов с ассоциированными конверсиями; фактические выкупы и прибыль
этой формулой не подтверждаются. Денежные поля `*_minor` — целые копейки.
При нулевой сумме заказов `drr_percent=null`, а не 0%.

Каждый ответ fullstats и нормализованные дни сохраняются как неизменяемая версия.
Текущая проекция выбирает последнее наблюдение по
`account_id + campaign_id + business_date`. Новый ответ заменяет ранее наблюдаемый
день, в том числе нулевой результат. Повторы, пересекающиеся периоды и разные
времена отчёта не складываются. Итоги дня/кампании берутся из родительских
счётчиков WB; строки приложений/товаров не прибавляются к ним.

Товарная разбивка публикуется только при совпадении всех аддитивных счётчиков с
итогом кампании. Несовпадение отражается в `unallocated_sku_days`; общий итог
остаётся доступен. SKU-строки тогда покрывают только подтверждённую часть.

Необходимо проверять `state`, `coverage` и `last_observed_at`:

- `missing_campaign_days` — день не получен, включая отсутствующий ID в ответе;
- `no_data_campaign_days` — успешно полученный WB результат без статистики;
- `unsupported_campaigns` — статусы, для которых fullstats не поддерживается;
- `complete_for_known_campaigns` — покрыты известные доступные кампании периода;
- `all_time_verified=false` — полнота всей истории кабинета не доказана.

Если WB пропустил ID в пакетном ответе, сборщик отдельно проверяет его в
сохранённой задаче. Успешный `null` подтверждает отсутствие статистики; повторно
пропущенный одиночный ID остаётся пробелом. Бесконечных повторов таких ID нет.

Список WB может не содержать давно удалённые кампании. Сборщик сохраняет ID из
прошлых манифестов, но не способен восстановить неизвестные ему удалённые ID.
Медиа-реклама из отдельного Media API также не входит в этот архив. Для
подтверждённого полного ДРР кабинета понадобится сверка со всеми историческими
ID/официальным экспортом и отдельное покрытие медиа-рекламы. История затрат
`/adv/v1/upd` здесь не добавляется к fullstats, чтобы расход не удваивался.

## Запуск

1. Применить миграцию `052_wb_advertising_history.sql` штатным мигратором
   position-db **до запуска нового MCP**. Контракт проверяется при старте/readyz.
2. Включить нужные WB кабинеты в существующей политике сбора
   `REPORT_COLLECTION_POLICY`; `enabled=true`. Указать их в реестре доступа.
3. Использовать существующую папку read credentials report-collector. Отдельные
   рекламные ключи записи не нужны. MCP использует существующее подключение
   `MCP_REPORT_REFRESH_DATABASE_URL` с ролью `report_refresh_requester`.
4. Добавить `compose.wb-advertising-history.yaml` к текущему стеку
   `compose.position.yaml` и включить профиль `wb-advertising-history`.
   Образ задаётся существующим `MCP_REPORT_COLLECTOR_IMAGE`.
5. Выполнить `advertising-history-preflight` и отправить MCP `sync` для кабинета.

Сборщик выполняет одну сохранённую задачу за квант: до 50 ID и 31 дня.
Он уступает текущему ежедневному сбору рекламы, использует его PostgreSQL gate
и общую квоту WbClient по токену/эндпоинту. На 429 сохраняет паузу WB в очереди;
не крутится в цикле запросов. Перезапуск восстанавливает незавершённую задачу
после истечения двухминутной аренды; результаты старой аренды не принимаются.
Для уже инициализированных кабинетов последние 30 закрытых дней обновляются
ежедневно, один раз на дату. Открытый день по московскому времени WB исключён.

После установки код доступен для всех разрешённых кабинетов. Само наличие кода
не означает, что production обновлён или история уже загружена.

## Проверка

```bash
cargo test --lib advertising_history --no-default-features
scripts/with-position-test-db.sh cargo test --test wb_advertising_history --no-default-features
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

Тесты PostgreSQL используют отдельную временную базу. Они проверяют продолжение
после потери аренды, пересечения и исправления дней, пропуски, точность ДРР,
изоляцию кабинетов и права ролей. Вызовов production или WB API в тестах нет.

Контракт полей WB сверяется с [официальной документацией Promotion API](https://dev.wildberries.ru/en/docs/openapi/promotion?locale=ru%2F).
