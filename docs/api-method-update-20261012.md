# Проверка методов API на 12 октября 2026

Изменения подготовлены в исходном коде. Этот документ не подтверждает выпуск
runtime, доступ всех кабинетов или полноту исторических данных.

## Реализовано

| Инструмент | Официальный запрос | Контракт |
|---|---|---|
| `wb_order_feed` | POST `/api/analytics/v1/order-feed` | Последние 31 день по времени текущего статуса; одна страница с `snapshotTime`, `offset`, `limit` до 10000. Статусы и причины отмен сохраняются раздельно. |
| `wb_supply_discrepancies` | GET `/api/supplies/v1/discrepancies/{supplyId}` | Положительный ID фактической поставки FBW. Только чтение расхождений. |
| `wb_item_returns` | GET `/api/analytics/v1/item-returns` | Возвраты и перемещения продавцу, `active`/`archive`, даты, limit/offset. HTTP 204 сохраняется как `no_data`. |
| `wb_promotion_budgets` | POST `/api/advert/v2/budget` | 1–50 уникальных ID. `total` в основных единицах `currency`; null и отсутствующие кампании не становятся нулями. |
| `wb_promotion_daily_limits` | GET `/api/advert/v0/daily-limits` | До 100 CPC-кампаний, ID через запятую. Персональный или Сервисный токен. |
| `wb_stock_history_create` | POST `/api/v2/nm-report/downloads` | Только `STOCK_HISTORY_DAILY_CSV`, последние 3 календарных месяца, уникальный UUID, фильтр SKU и тип склада. |
| `wb_analytics_report_status` | GET `/api/v2/nm-report/downloads` | Проверка одного UUID через `filter[downloadIds]`, без фонового опроса. |
| `wb_analytics_report_download` | GET `/api/v2/nm-report/downloads/file/{downloadId}` | Готовый отчёт доступен 48 часов. ZIP читается в памяти, UTF-8 CSV возвращается в `files[].csv`; до 4 файлов и 2 МиБ суммарно. Превышение лимита — ошибка без частичных итогов. |

`wb_promotion_budget` сохраняет параметр одной кампании и поле `total` для
совместимости с Control, но использует v2. Адаптер проверяет ID, целое
неотрицательное значение и RUB: существующая автоматизация переводит рубли
в копейки. Ошибочная валюта или отсутствующий бюджет останавливают проверку.
Старый GET `/adv/v1/budget` исключён из разрешённых запросов.

Поисковые инструменты WB и описание `date_from` теперь указывают обновление
раз в два часа, действующее с 12 октября. Дневная история остатков также
обновляется раз в два часа и не требует подписки «Джем».

Новые инструменты используют существующие проверки доступа, классификацию
недоверенных данных и удаление персональных полей, включая `srid`. Данные
доставки и идентификаторы покупателей не предназначены для вывода менеджеру.
Подключение order feed к фоновому сборщику с дедупликацией — отдельная работа;
текущие инструменты предоставляют страницы официального API.

Тип токена определяется локально по документированным JWT-полям `acc`, `for`,
`t`, `s`, `exp`; токен не передаётся внешнему декодеру. Для Персональных
токенов с нужной категорией применяются официальные интервалы:
order feed 1 минута, бюджеты 3 секунды, создание/статус/скачивание отчёта по
20 секунд каждый. Декодирование выбирает только частоту и не заменяет
авторизацию WB. Для Базовых, истёкших, тестовых и нераспознанных токенов
сохранены консервативные интервалы: 3 часа, 15 минут и по часу соответственно.
Действующая конфигурация принимает только Персональные токены. Сервисные и
Базовые токены с секретом не ускоряются: отправка секрета и привязка сервиса
не реализованы. Их локальная классификация не добавляет поддержку подключения.
Для чтения дневных лимитов используется интервал 12 секунд. Создание, статус
и скачивание имеют отдельные квоты, поэтому создание не блокирует проверку
готовности. Скачивание выполняется после `status=SUCCESS`, не после
`WAITING`/`PROCESSING`. WB ограничивает генерацию 20 отчётами в сутки.
Длинные cooldown возвращаются немедленно; ошибки не повторяются
автоматически. Локальная и общая межпроцессная квоты используют одинаковый
выбор интервала. Длительный `Retry-After` сохраняется для последующих вызовов
независимо от типа токена, до максимального срока 24 часа.
Короткий интервал бюджета ожидается в пределах срока запроса, чтобы
последовательные проверки запуска/пополнения не завершались ложной ошибкой
локальной квоты. Ожидание не удерживает сетевые разрешения.

Локальная проверка семи настроенных WB-токенов подтвердила Персональный тип,
срок действия, категории аналитики/продвижения и доступ только для чтения.
Это подтверждает выбор быстрых интервалов, но не доступность каждого нового
метода upstream. Токены при проверке не выводились и не отправлялись декодеру.
Расхождения поставок используют существующую общую квоту группы FBW — 1 час;
полная схема и отдельная квота нового метода ещё не подтверждены.
Для CSV больше лимита нужно сузить период или фильтр `nm_ids`.

## Ozon: что подтверждено и что осталось

- Акты FBO `/v1/supply-order/act/summary/get` и `product/get` анонсированы
  11 августа; `/v1/analytics/stocks` получил данные реального времени и новые
  поля; `shipment-plan-compliance/get` анонсирован 9 октября.
- Старые акции отключаются 13 октября с изменением поведения v2. Действующая
  allowlist MCP вообще не содержит маршрутов акций: сейчас это недостающий
  источник чтения, а не сломанная миграция существующего адаптера.
- Публичные `docs.ozon.ru` и `dev.ozon.ru` во время проверки возвращали
  циклические перенаправления/HTTP 403. В локальной Postman-коллекции нужных
  новых контрактов нет. Эти методы не добавлены без проверенной схемы запроса,
  обязательных параметров, пагинации и границ. Нужен актуальный официальный
  OpenAPI/экспорт документации либо восстановление доступа к документации.
- Финансовый сборщик уже использует `/v1/finance/accrual/by-day`. Описания
  двух старых MCP-инструментов v3 уточнены: объявленное отключение с 8 сентября,
  рекомендуемые accrual-методы и отсутствие эквивалентности старым totals.
  Legacy-контракты сохранены для совместимости и не означают гарантированный
  доступ upstream.

## Проверка FBO у Артёма

Повторный read-only вызов `ozon_fbo_postings` для
`mebelnaya_furniturnaya_kompaniya` за 11 октября с `limit=1` успешно вернул
отправление, `has_next=true` и cursor. Использовался `/v3/posting/fbo/list`.
Ошибка 400 из исходного сообщения не воспроизвелась. Добавлена проверка
контракта с limit=1; доказательств для изменения допустимого лимита нет.
