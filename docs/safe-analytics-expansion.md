1. Добавлен `MCP_DATA_MODE=reporting_only`: процесс не импортирует соседний
   `.env`, не загружает ключи маркетплейсов и исключает прямые Ozon/WB-методы

2. Проверен финансовый сборщик Ozon: он уже обращается к новым `/types`
   и `/by-day`. Исправлена классификация платной рекламы и неоднозначного
   идентификатора начисления. Неизвестный тип сохраняет сумму и признак
   неизвестности. Новая версия checkpoint исключает повторное использование
   страниц, классифицированных прежним способом.
3. Добавлены фиксированный HTTP-клиент и сборщик подробных финансовых строк WB.
   Только `POST /api/finance/v1/sales-reports/detailed` на разрешённом домене,

   до HTTP 204. Сохраняются пропуски и неизвестные виды операций; персональные

## Выделенный процесс MCP

`compose.analytics-reader.yaml` — самостоятельное описание нового сервиса,
не overlay для старого `compose.yaml`. Оно не монтирует `.env` или каталог
секретов маркетплейсов, требует JWT и подключает только явно выбранную сеть
PostgreSQL. Порт по умолчанию — loopback 8789, отдельно от действующего MCP.

До запуска необходимо проверить:

- образ соответствует проверенной версии; registry содержит только метаданные;
- выбранная внешняя Docker-сеть действительно имеет `Internal=true`;
- доверенный HTTPS JWKS доступен внутри неё; текущий JWT-клиент не использует
  системный HTTP proxy, поэтому одной переменной proxy недостаточно;
- URL PostgreSQL использует ограниченную роль чтения опубликованных views;
- новая точка входа проверяет подпись, issuer, audience, scope и доступ
  сотрудника к кабинету; VPN не заменяет эти проверки.

Если внутреннего сервиса идентификации/JWKS нет, этот профиль ещё не готов к
запуску. Не следует добавлять ему общий интернет-доступ ради обхода проверки.
Сетевую изоляцию и фактические права PostgreSQL надо подтвердить на стенде.
Шаблон не создаёт сеть и сам по себе не доказывает её изоляцию.

Очередь обновления и журнал вызовов используют отдельные узкие права записи
в локальную БД. Шаблон требует второй URL роли `report_refresh_requester` для
этих операций; права чтения бизнес-данных остаются у reader. Подключение
обеих ролей и журналирование нужно проверить на стенде. Успешная загрузка настроек не
доказывает права ключей, подписки, свежесть или полноту данных.

## Следующие законченные этапы

| Этап | Работа | Доказательство готовности |
| --- | --- | --- |
| Финансовая история WB | Версионированные строки отчёта, report/row ID, кабинет, период, валюта, исходная точность и проверяемое происхождение; атомарная публикация после последней страницы | Повторный сбор не удваивает суммы; ошибка страницы не публикует полный отчёт; итоги сходятся с WB |
| Финансовая детализация Ozon | Подтвердить текущую схему начислений и услуг; хранить идентификаторы и компоненты без двойного счёта | Обезличенный эталон ответа и сверка агрегатов с отчётом; доля неизвестных типов видна |
| Проверка ключей | Отдельный пробный вызов нужного Finance-метода для каждого явно выбранного кабинета | Подтверждены доступ, тип токена, ограничения и ответ; 401/402/403 не вызывают подмену ключа |
| Надёжное расписание | Сохранять квоты и Retry-After между страницами и перезапусками, повторно проверять разрешённый кабинет | Перезапуск не обходит паузу; можно остановить источник; неполные загрузки видны |
| Поиск Ozon и реклама | Проверить текущие схемы `/v1/analytics/product-queries` и `/details`, подписку, лимиты, историю рекламы до SKU | Ограниченные запросы, сохранённая история, отдельно факт и атрибуция |
| Себестоимость 1С | 1С сама отправляет ограниченную выгрузку в отдельный приёмник; идентификатор выгрузки, хеш, SKU/кабинет, валюта, НДС, способ распределения и период действия | Повтор безопасен, конфликт периодов отклоняется, источник каждой себестоимости известен |
| Отчёты | Читать согласованные периоды продаж, запасов, цен, финансов, рекламы и себестоимости | При пропусках прибыль/ABC/XYZ/пополнение явно недоступны или ограничены; N/D не равен нулю |

В БД уже есть таблица `unit_economics_inputs`, но готового Rust-импорта и
чтения её себестоимости нет. Для воспроизводимой истории требуется дополнить
происхождение записей и правила пересечения периодов. Доступ Ubuntu к офисной
сети, Windows Server, SQL и 1С для этого не требуется.

Новые методы WB используют консервативный интервал 12 часов. Операторский
сборщик сохраняет его на диск вместе с Retry-After и продолжает страницы
при следующих явных запусках. Автоматический scheduler ещё не включён;
переход на более частую квоту проверенного Personal-токена требует
отдельной настройки и проверки. Автоматического перехода на read-write
или ADMIN-ключи нет.
