# Рекламные данные MCP ОФК: подготовка, сверка и журнал

Эти команды работают локально с явно переданными JSON. Они не используют
ключи кабинетов, переменные окружения, PostgreSQL или сетевые вызовы.
Загрузку через MCP ОФК выполняет вызывающий процесс с его проверкой доступа.
Автоматическое расписание и применение ставок в этот этап не входят.

## Воспроизводимый запуск

Все файлы `config/*example.json` ниже синтетические. Пороги и бюджеты в них
показывают формат, а не задают стратегию действующего магазина.

```bash
cargo run --locked --bin ads-optimizer -- prepare config/ads-optimizer-prepare.example.json > prepared.json
cargo run --locked --bin ads-optimizer -- reconcile config/ads-optimizer-reconciliation.example.json > reconciliation.json
mkdir -m 700 ads-runs
cargo run --locked --bin ads-optimizer -- recommend prepared.json --journal-dir ads-runs/run-001 > recommendation.json
```

Пример подготовки содержит два дневных снимка, полученных на следующий день.
С запасом атрибуции семь дней результат — `hold`, ноль зрелых дней. Более
поздний запуск не добавляет в сохранённые снимки новые заказы. Пример сверки
показывает арифметическое совпадение daily с direct+model, но оставляет
`semantic_equivalence_verified: false`.

Старый `recommend evidence.json` продолжает работать без записи файлов.
Обычные входы ограничены 4 МиБ, bundle для `prepare` — 32 МиБ. Символические
ссылки и директории вместо входных файлов отклоняются. Готовый evidence
также ограничен 4 МиБ. Ошибки не печатают содержимое и пути входных файлов.

## Подготовка полного экспорта

[Синтетический bundle](../config/ads-optimizer-prepare.example.json) содержит
`version: 1`, один `account_id`, `as_of`, границы дат, `objective`, `policy`,
список `products`, `advertising_pages` и необязательный `stock_pages`.
Каждая страница — `{ "offset": 0, "response": <исходный ответ> }`.
В `response` сохраняется объект результата `ofk_source_snapshot`, без
внешней MCP-обёртки `content/structuredContent` и без изменения строк.

1. Получить первую страницу `ofk_source_snapshot(source=advertising)`.
2. Следовать `next_offset`, передавая один и тот же `snapshot_id` из первой
   страницы, пока `next_offset` не станет `null`.
3. Так же получить полный снимок `source=stocks`, если он используется.
4. Для истории передать сохранённые полные снимки каждого дня. Метод чтения
   последнего снимка сам по себе не загружает и не восстанавливает историю.
5. Проверить модели оплаты и полный состав кампаний выбранных SKU отдельно;
   заполнить `cpc_scope` и сохранить экспорт, подтверждающий эту проверку.

Для каждого продукта нужны SKU, текущий и максимальный дневной аналитический
лимит, `budget_constraint`, `economics` и `cpc_scope`. В режиме рекламной ДРР
`economics` может быть `null`. В scope задаются `campaign_ids`,
`pricing_model: cpc`, `source_ref`, реальный `observed_at` проверки и
`all_campaigns_confirmed`. Это явное утверждение оператора, а не результат
проверки ссылки самим CLI. Модель оплаты нельзя выводить из наличия кликов.

Подготовка проверяет все страницы и происхождение всех строк, включая
невыбранные SKU. Проверяются аккаунт, маркетплейс, источник, ID снимка,
cutoff, наблюдение, статус и полнота; интервалы рекламы должны охватывать
полные дни Екатеринбурга. Пересекающиеся снимки, повторы строк, пропущенные
страницы и чужие кампании выбранного SKU отклоняются.

Покрытие кампаний проверяется по каждой паре **кампания × день × выбранный
SKU**. Отсутствующая пара делает `coverage_complete: false`; частичная сумма
остаётся видимой, но не допускает решения по эффективности. Нулевой вклад
принимается только из явной нулевой строки. `modelOrders/modelSales` не
добавляются к прямым заказам и выручке оптимизатора.

`observed_from` сохраняется в каждом дне как консервативное начало наблюдения
его снимка. Максимум `observed_from` по снимкам попадает в общий `observed_at`.
Зрелость и свежесть проверяются по собственному времени каждой строки.
Поэтому свежая последняя страница не делает старые дни свежими или зрелыми.
Отсутствие `observed_from` не компенсируется временем экспорта.

## Идентификаторы и доступность остатков

Импорт различает три формата по `warehouse_id`:

- `fbo:<id>` / `fbs:<id>` — реальные склады с Ozon SKU и нормализованным
  доступным количеством.
- `sku-fulfillment-v2:fbo`, `sku-fulfillment-v2:fbs`,
  `sku-fulfillment-v2:rfbs` — исправленный резервный сборщик
  `/v4/product/info/stocks`. SKU берётся из `stocks[].sku`, количество — из
  `present - reserved`. Это итог по схеме исполнения, а не физический склад.
- `FBO`, `FBS`, `RFBS` — исторический резервный формат: в поле `sku` был
  записан `product_id`, а количество включало резервы. Эти строки нельзя
  использовать для рекомендаций даже при случайном числовом совпадении ID.

Для нового резервного формата обязательны настоящий SKU и оба счётчика.
Отсутствующие значения, резерв больше наличия, повтор SKU/схемы и неизвестные
типы отклоняются. FBO/FBS/rFBS разных SKU одного product_id не склеиваются.
Полные итоги по схемам и строки физических складов нельзя смешивать в одном
снимке: это может удвоить остаток. Отсутствие SKU в снимке остаётся неизвестным
остатком, а не нулём.

Если в снимке есть хотя бы одна строка исторического формата, весь stock-снимок
остаётся неизвестным (`stock: null`) с причиной
`unsupported-legacy-stock-identity:<snapshot_id>`. Исторические снимки не
переписываются. Новые страницы резервного сборщика имеют отдельный ключ
checkpoint: старые сохранённые product_id/количества не воспроизводятся как
исправленные данные после обновления программы.

Исправление кода требует развёртывания сборщика и публикации нового полного
снимка, прежде чем новые остатки станут доступны через MCP ОФК. Локальный тест
или успешное чтение одной страницы не подтверждают готовность всего кабинета.
Основания, проверки и порядок проверки после выпуска описаны в
[заметке об исправлении остатков](ozon-stock-identity.md).

## Сверка двух рекламных отчётов

[Пример](../config/ads-optimizer-reconciliation.example.json) принимает два
отдельных нормализованных источника: опубликованный SKU-отчёт и дневной
отчёт кампаний. Оба содержат аккаунт, ссылку происхождения, фактическое время
наблюдения, признак полноты и строки. Деньги передаются целыми копейками.

В SKU-строках отдельно указаны прямые и модельные заказы/выручка. В строках
кампаний сохраняются собственные orders/revenue без переименования их в
прямую атрибуцию. Суммирование выполняется по кампании и дате на полном
наборе SKU выбранной кампании. Дубликаты и чужой период отклоняются.

Вывод всегда `diagnostic_only`: суммы источников, разницы и отдельная
арифметическая проверка direct+model. Отсутствующая сторона даёт `null`,
а не нулевую выручку. Разные времена наблюдения и неполнота видны в reasons.
Знаковые разницы сериализуются десятичными строками, чтобы не потерять
точность при чтении JSON. Совпадение чисел не доказывает равенство определений
атрибуции и не разрешает объединять показатели разных отчётов.

## Журнал запусков

`--journal-dir` принимает путь к **новому** каталогу внутри существующего
каталога оператора. Родитель не должен быть ссылкой или доступен на запись
группе/остальным пользователям. Каталог запуска создаётся с правами 0700,
файлы — 0600. Существующий путь, включая пустой каталог, не перезаписывается.

В журнале три файла:

- `evidence.json` — точные байты входного evidence;
- `report.json` — точные байты JSON, отправляемого в stdout;
- `manifest.json` — версия программы, аккаунт, цель, исходные даты,
  отдельное фактическое `recorded_at`, размеры и SHA-256 обоих файлов.

Перед записью отчёт пересчитывается и сверяется с входом. Manifest пишется
последним после сохранения данных на диск. При ошибке частичный каталог
остаётся для разбора, повторный запуск требует нового пути. Завершённость
проверяют по валидному manifest, длинам и хешам файлов; одного наличия
каталога или manifest недостаточно.

Хеш исходного файла отличается от канонического `input_sha256`: первый
учитывает форматирование JSON, второй — нормализованные данные расчёта.
Хеши не являются подписью или разрешением на рекламное действие. Владелец
файлов технически может изменить их вручную; это не WORM-хранилище.
Bundle и исходные выгрузки по `source_refs` архивируются отдельно: журнал
рекомендаций сохраняет подготовленный evidence, а не все внешние источники.
