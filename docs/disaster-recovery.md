# Восстановление основного MCP

Область этого сценария: один владелец, read-only MCP, PostgreSQL с сохранёнными
данными, архивы отчётов и закрытый туннель. Коллекторы, доставка отчётов и
рекламные исполнители запускаются по своим отдельным процедурам. Их наличие на
старом Mac не означает разрешение автоматически запустить их на втором хосте.

## Что хранить вне Mac

Один комплект состоит из:

1. `position-db.dump.age`, `report-artifacts.tar.age` и их `manifest.json` из
   одного успешного запуска `backup-position-stack.sh`. Для установки со
   static Ozon guard формат v3 также содержит `ozon-guard-state.tar.age`.
   Все три архива должны относиться к одному комплекту.
2. Зашифрованного `recovery.tar.age` с конфигурацией того же развёртывания:
   env, реестр доступа, профиль и runtime key туннеля, LaunchAgents, установленные
   служебные скрипты, Compose и подтверждения immutable release.
3. Независимо сохранённого ключа расшифрования age. Его нельзя упаковать в архив,
   для открытия которого нужен этот же ключ. Ссылка на место хранения ключа
   помогает оператору, но сама по себе не доказывает, что ключ там есть.
4. Проверенной копии инструмента `scripts/recovery-bundle.py` из соответствующего
   Git commit: это несекретный загрузочный инструмент для проверки и распаковки.

Recovery bundle использует явный список файлов, шифруется age и распаковывается
только в новый закрытый каталог. Он не перезаписывает рабочие настройки и не
запускает сервисы. Не публикуйте расшифрованный каталог, логи окружения или ключи.
Хранилище должно сохранять несколько поколений: синхронное зеркало единственной
копии не защищает от ошибочного удаления.

## Согласованный бэкап static Ozon guard

`backup-position-stack.sh` обнаруживает том `guard-state` по Compose-метке или
суффиксу имени `-guard-state`. Для ручного запуска можно явно указать том через
`MCP_BACKUP_GUARD_STATE_VOLUME`. Установщик `install-operations-agents.sh`
сохраняет это значение и для первого бэкапа, и в плановом LaunchAgent. Пустое
значение сохраняет автообнаружение; несколько найденных томов блокируют запуск.
Неоднозначный выбор тома, отсутствие состояния
при наличии static guard audit в БД или несколько аккаунтов в этом журнале
требуют отдельной процедуры восстановления; неполный комплект не публикуется.

Guard удерживает файловую блокировку весь срок работы. Полный бэкап требует
согласованного окна обслуживания: оператор останавливает исполнителя по его
runbook, запускает бэкап, затем возвращает исполнителя после проверок.
Скрипт самостоятельно исполнителя не останавливает. Остановка процесса guard
сама по себе не останавливает расход кампании; это учитывается при выборе окна.
Обычное ежедневное расписание без такого окна пока не обеспечивает бэкап guard.

Бэкап получает ту же эксклюзивную блокировку и удерживает её во время снимка БД
и копирования `state.json`. Курсор журнала проверяется до и после `pg_dump`.
Файл сохраняется целиком, включая незавершённые действия и инциденты; файл
PID/lease и временные файлы в архив не входят. Проверка восстановления требует
приватных прав, побайтного сохранения состояния и совпадения курсора с журналом
восстановленной БД. Полную семантическую проверку JSON выполняет guard при старте;
успешная распаковка не является разрешением повторить неоднозначное действие.

Установки без guard и без его audit в БД сохраняют формат v2. Старые v1/v2
проверяются как комплект БД и отчётов; `guard_state_verified: false` явно
обозначает отсутствие подтверждённого восстановления guard. Наличие внешней
копии и независимого ключа age проверяется отдельно от формата архива.

## Проверка комплекта

```bash
python3 scripts/recovery-bundle.py verify \
  --bundle /ABS/recovery.tar.age --identity /ABS/recovered-age-identity.txt
python3 scripts/recovery-bundle.py extract \
  --bundle /ABS/recovery.tar.age --identity /ABS/recovered-age-identity.txt \
  --output-dir /ABS/new-private-recovery-directory
MCP_BACKUP_AGE_IDENTITY_FILE=/ABS/recovered-age-identity.txt \
  bash scripts/verify-position-backup.sh /ABS/one-backup-directory
```

Последняя команда восстанавливает БД и проверяет ссылки на артефакты только в
одноразовом контейнере. Контейнер не подключён к рабочей сети. Для реального
восстановления нужна копия, заново скачанная из внешнего хранилища, и ключ,
полученный из независимого места хранения. Повторная проверка локальных файлов
не подтверждает восстановление после потери Mac.

## Проверка аварий на отдельном стенде

`scripts/runtime-recovery-drill.py` принимает два ранее проверенных image lock и
локальный immutable image PostgreSQL с установленной схемой. Он создаёт только
ресурсы со случайным префиксом `mcp-recovery-drill-`, внутреннюю Docker-сеть,
одноразовый том и синтетические учётные данные. Marketplace credentials не нужны.

```bash
python3 scripts/runtime-recovery-drill.py \
  --current-lock /ABS/current/release-images.json \
  --rollback-lock /ABS/previous/release-images.json \
  --postgres-image sha256:LOCAL_INITIALIZED_SCHEMA_IMAGE_ID \
  --evidence /ABS/new-drill-evidence.json
```

Проверяются готовность и реальный read-only MCP-запрос, недоступность БД с
последующим восстановлением соединения без перезапуска MCP, запуск остановленного
контейнера watchdog, откат образа и возврат на текущую версию. До и после сверяются
существовавшие Docker-контейнеры. Данные и процесс настоящего туннеля не меняются:
его HTTP-протокол здесь воспроизводит локальная заглушка. Отдельные contract tests
watchdog проверяют потерю poll, cooldown, ограничение ожиданий и блокировку запусков.

## Реальная авария

1. Установить масштаб сбоя по внешнему уведомлению, локальным health/readiness,
   свежести poll и журналам. Сохранить сведения о версии и ошибке.
2. При сбое процесса использовать установленный watchdog. При потере Mac
   подготовить чистый хост, проверить и распаковать внешний комплект.
3. Восстановить БД и артефакты из одного комплекта. Оставить исполняющие рекламные
   процессы выключенными. Проверить аутентификацию БД и согласованность архивов.
4. Восстановить конфигурацию в постоянные закрытые каталоги и проверить права.
   Скачать точные образы по digest; сверить source SHA и release evidence.
5. Запустить MCP и проверить `/livez`, `/health`, `/readyz` и read-only MCP-запрос.
   Подключить единственный экземпляр туннеля после остановки старого экземпляра.
   Проверить `/healthz`, `/readyz` туннеля и успешный poll не старше 90 секунд.
6. Проверить уведомление о восстановлении и новый внешний backup. Зафиксировать
   фактическое время простоя и возраст восстановленных данных.

Откат только бинарника MCP использует предыдущий подтверждённый immutable image
и сохранённую конфигурацию. Он не требует отката production БД. Для нового релиза
перед откатом отдельно проверяется совместимость с текущей схемой БД.

## Границы автоматического восстановления

macOS LaunchAgents работают в пользовательской GUI-сессии. `RunAtLoad` и
30-секундный watchdog восстанавливают runtime после входа пользователя; это не
обещание запуска до входа или разблокировки FileVault. Проверка выключения всего
Mac выполняется в согласованное окно и требует внешнего наблюдателя.

При ежедневном backup ориентир по потере данных — не более суток, если задания
успешны и Mac доступен. Фактический RPO определяется последней проверенной
внешней копией. Время полного восстановления на новом Mac измеряется отдельно;
быстрый рестарт контейнера не доказывает такой RTO.

Завершение: доставлено тестовое уведомление о сбое и восстановлении; внешний
наблюдатель обнаруживает пропущенный heartbeat; комплект скачан с внешнего
хранилища и восстановлен с независимо сохранённым ключом; сохранён успешный
протокол изолированных аварийных испытаний. Отсутствующие внешние адреса или
доступы записываются как незавершённые пункты, а не как успешная проверка.
