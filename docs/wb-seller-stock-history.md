# История остатков на складах продавца WB

Текущий сборщик сохраняет два независимых источника: `stocks` для FBW на складах
WB и `seller_stocks` для складов продавца. Сбой одной части не запрещает публикацию
другой. Новый источник продавца остаётся дополнительным: он не меняет четыре
обязательных источника отчёта WB и не прибавляет свои количества к текущим FBW.

## Охват и чтение

Сборщик использует список складов `GET /api/v3/warehouses`, карточки вне корзины
`POST /content/v2/get/cards/list` по 100 записей и остатки
`POST /api/v3/stocks/{warehouseId}` пакетами до 1000 `chrtIds`.
[Контракт WB](https://dev.wildberries.cn/docs/openapi/item-management) описывает
операции чтения. Для них нужен доступ ключа к Content и Marketplace.

Сохраняются соответствие `chrtID → nmID`, отдельная строка на размер и склад,
а также положительный `delivery_type` из ответа WB. Значение 1 обозначает FBS;
остальные типы доставки сохраняются явно. Их нельзя называть FBS без фильтра.
Карточки из корзины не входят в каталог этого сбора. Метка
`catalog_scope="active_non_trash_cards"` описывает именно этот охват.

Используйте `ofk_source_snapshot` с `source="seller_stocks"`. Ответ имеет
`inventory_scope="seller"`; строки содержат `sku`, `chrt_id`, `warehouse_id`,
`delivery_type` и `sellable_units`. Для следующих страниц закрепите `snapshot_id`.
Coverage показывает известные и неизвестные пары во всём снимке, а не только
на странице. Сохраняются время наблюдения, состояние данных и свежесть.
История начинается с фактических наблюдений: текущая выгрузка не доказывает
остаток на прошлую дату.

Явный `amount=0` сохраняется как ноль. Если WB пропустил запрошенный размер,
`sellable_units` остаётся NULL. После выполнения всех пакетов такой снимок
публикуется как `partial` с завершённой пагинацией. Reader может вернуть его
с отдельным качеством `partial` или `stale`; предыдущие полные снимки остаются
доступны по их ID. Незавершённая пагинация не выдаётся за полный охват. Пустой
результат имеет `data_state="no_data"` и не означает доказанный нулевой остаток.

## Совместимость с прежней историей

PR 102 и миграция 037 вводили совместное задание Stocks: FBW и склады продавца
должны были закончиться до публикации одного снимка. Этот порядок заменён
отдельным заданием и снимком `seller_stocks` в миграции 039.

Ранее опубликованные снимки `stocks` не переписываются. В них могут остаться
пространства имён `warehouse_id`:

- `wb:123` — склад WB;
- `wb:seller:1:123` — склад продавца с FBS;
- `wb:seller:2:123` — склад продавца с другим сохранённым типом доставки.

Если в историческом снимке есть хотя бы одна строка `wb:seller:*`, reader
помечает весь снимок `inventory_scope="mixed"`, даже если текущая страница
содержит только FBW. Новые `stocks` собирают только FBW. Новые `seller_stocks`
используют числовой ID склада и отдельное поле `delivery_type`.

## Продолжение и пределы

Плановый сбор и разрешённое менеджеру обновление создают независимое
дополнительное задание `seller_stocks` вместе с WB `stocks`; миграция 039
разделяет их выполнение и публикацию.

Страницы сохраняются в PostgreSQL под арендой задания. Один квант допускает
один новый HTTP-запрос. Миграция 037 разделяет квоты Analytics, Content и Seller
Inventory; новый независимый источник использует нужную группу по этапу.
`Retry-After` сохраняется, потерянная аренда не разрешает новый запрос.
Успешные пакеты повторно читаются из журнала, а не запрашиваются у WB.

Пределы: 100 складов, 25000 размеров, 25000 агрегированных пар SKU/склад и
до 2500000 строк размер/склад. Срок наблюдения остатков остаётся 30 минут:
эти пределы не обещают выгрузить максимальный каталог за это время. Превышение
лимита, чужие ID, повторы, отрицательные количества или сломанный курсор
завершают источник ошибкой без обрезания и подмены неизвестных значений нулями.

Миграция **038** сохраняет успешные страницы неудачного сбора для диагностики
и точного восстановления оператором после устранения причины. Миграция **039**
добавляет отдельный источник `seller_stocks`, таблицу фактов и представление
для чтения. Они применяются после существующих 036–037. Во время перехода
прежний сборщик останавливается; после миграций запускаются обновлённые
collector, MCP server и reporting egress. Старый совместный сборщик не должен
параллельно публиковать снимки. Подробнее: [сбор остатков](wb-stock-collection.md)
и [восстановление checkpoint](stock-checkpoint-recovery.md).

Эта реализация не меняет остатки в кабинете WB. Фактические права ключа,
время выполнения и охват каждого кабинета подтверждаются результатами его
плановых заданий после отдельного выпуска.
