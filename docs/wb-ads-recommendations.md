# Ежедневные предложения по рекламе WB без 1С

`wb_ads_recommendations` связывает перечитанную историю выбранных кампаний
с текущими настройками, опубликованными остатками FBW и отдельным срезом
заказов магазина. Результат — объяснимые предложения для проверки менеджером.
Ставки, бюджеты, кампании, политики Control и расписания метод не меняет.

Область анализа Агзамовой с выбранным пользователем целевым ДРР 15%:

```json
{
  "account": "ofk_region_wb",
  "campaign_ids": [39807762, 40141836],
  "days": 30,
  "target_drr_bps": 1500,
  "limit": 50
}
```

Перед вызовом подтвердите актуальные ID через `wb_promotion_campaigns`.
`target_drr_bps` — необязательная явно выбранная рекламная цель: 1500 означает
15%. Без цели числовых предложений ставки нет; расходы без заказов всё равно
могут дать задачу проверить воронку. Допустимый ДРР метод сам не назначает.
Это не порог безубыточности: себестоимость и чистая прибыль не рассчитываются.

## Источники и период

Доступны 1–10 кампаний и 7, 14 либо 30 закрытых дней по `Europe/Moscow`.
В результате видны окна 7/14/30, помещающиеся в запрошенную историю.
Решение использует 14 дней, если они доступны, иначе 7. Окно 30 дней служит
дополнительным контекстом. История WB перечитывается через общий лимитер:
один запрос настроек и один fullstats. Ответ не записывается в долговечный
архив и не меняет результат `wb_advertising_history_status`.

Метод сначала читает все страницы `stocks` и `sales` из PostgreSQL, закрепляя
ID каждого снимка. Предел — 25 000 строк на источник; неполный экспорт,
дубликаты складов и чужой кабинет не принимаются. Недоступная БД и ошибки WB
возвращаются вызывающему; автоматического обхода квоты или повторных запросов нет.
Слишком большой fullstats требует уменьшить число кампаний или длину окна.

Решения используют **итоги кампании**, включая связанные покупки:
`decision_basis=campaign_totals`, `campaign_windows`. `windows` отдельно
показывает наблюдаемую товарную разбивку. ДРР отдельного SKU не считается
полным эффектом его рекламы: связанные заказы могут находиться в других строках.
Эти два уровня не складываются. Пропуски блокируют предложение
только для затронутой кампании. Несогласованная разбивка не распределяется
условно между SKU. `no_data_days` остаются отдельным наблюдением отсутствия
статистики, а не доказательством нулевых продаж.

Заказы WB включают связанную рекламную атрибуцию. Это заказанная выручка,
не выкупы, выплата продавцу или прирост от алгоритма. `recent_store_ordered_units`
берётся отдельно из опубликованного `sales`; его точный период показан в
`sales_period_start/end`. Суточный отчёт магазина по Екатеринбургу не
прибавляется к рекламному окну по Москве.

## Правила первой версии

- День допускается в метрики только после конца московских суток плюс
  72 часа **на момент фактического чтения WB**. Повторный запуск старого JSON
  не добавляет поздние заказы. Три дня — консервативная политика этой версии,
  а не утверждение о гарантированной окончательности атрибуции WB.
- Для сигнала эффективности нужны не менее трёх наблюдаемых дней кампании,
  30 кликов и трёх заказов. Это проверяемые пороги правил, не статистическая
  модель вероятности покупки и не доверительный интервал.
- ДРР выше цели более чем на 10% относительно цели даёт `review_decrease`
  с предложением шага −5%. Ниже цели более чем на 10% — `test_increase`
  с шагом +5%. Внутри коридора — `hold`. Сравниваются точные суммы;
  отображаемый ДРР в bps округляется вниз.
- Не менее 100 зрелых кликов и расход без рекламных заказов дают задачу
  проверить воронку и связанные продажи, без числовой ставки или остановки.
- Числовое предложение шага доступно только для активной кампании с одним
  текущим SKU, когда его суммы и число наблюдаемых дней совпадают с кампанией,
  для ручного CPC только в поиске, без размещения в рекомендациях. Несколько
  текущих SKU или несовпадение атрибуции дают `campaign_level_attribution`.
  В этих случаях, а также для смешанных размещений или
  CPM возможна задача `review_decrease` по общей эффективности, без числового
  шага: смешанная статистика не определяет ставку именно в поиске.
  Старый состав и отсутствующий текущий товар дают `hold`.
- Настройки должны быть не старше 30 минут, перечитанная рекламная история —
  часа, полный FBW — часа. Отсутствие строки SKU означает неизвестное наличие.
  Явный FBW-ноль требует отдельной проверки FBS и не означает общий stockout.
- Для повышения нужен свежий полный суточный срез заказов, а запас FBW должен
  покрывать не менее трёх таких суточных объёмов. Это ориентир по последним
  суткам, не прогноз спроса. FBS в расчёт FBW не прибавляется.

`suggested_step_bps` описывает относительный шаг ставки. Это не новая ставка,
не проверка минимальной ставки WB, не лимит из действующей политики и не
разрешение Control. Перед пилотом нужны отдельная проверка действующих лимитов,
минимальной ставки, свежих данных и авторизация.

Ответ содержит до `limit` строк (1–100, по умолчанию 50), сначала задачи
снижения, затем кандидаты роста, затем удержание. `total_recommendations` и
`truncated` показывают полный размер расчёта. Для большего охвата сузьте список
кампаний: живые ответы не выдаются за неизменяемые страницы одного отчёта.

## Воспроизведение и включение

```sh
cargo run --offline --locked --bin ads-optimizer -- recommend-wb config/wb-ads-recommendations.example.json
```

Пример синтетический; живые экспорты храните вне Git. CLI принимает сохранённые
ответы WB и полные экспорты снимков, не загружает окружение или ключи и не
обращается к сети. `source_sha256` связывает результат с сериализованными входными данными
(порядок полей и пробелы исходного файла не сохраняются).
Подлинность переданного файла проверяет экспортёр; CLI не заменяет серверный RBAC.

MCP-метод доступен finance/admin после проверки кабинета и live WB доступа.
В режиме `reporting_only` его нет: этот режим не обладает ключами площадки.
Для ежедневной работы метод можно вызывать после завершения свежего сбора;
данная версия сама не устанавливает таймер и не включает управление рекламой.
Публикация инструмента в работающем MCP требует обычного выпуска приложения.

`auto_apply_allowed=false`, `attribution_finality_verified=false` и
`causal_effect_verified=false` сохраняются во всех ответах. Следующий этап —
контролируемый пилот с проверкой заказов, расходов и ДРР против контрольной группы.
