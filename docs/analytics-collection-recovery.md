# Восстановление сбора продаж и детализация рекламы WB

Изменение устраняет три препятствия в существующем контуре аналитики:
пересечение страниц продаж, потерю SKU из Fullstats v3 и отказ всего периода
истории из-за старого снимка с неверными датами строк. Интеграция с 1С сюда
не входит.

Следующий этап добавляет [остатки всех складов продавца WB](wb-seller-stock-history.md)
и [сбор финансовых отчётов за период](wb-finance-period-sync.md).
Миграция 037 нужна для отдельных ограничений запросов Content и Seller Inventory.

## Продажи Ozon и WB

Сборщики проверяют уникальность пары `(business_date, sku)` при обходе страниц.
Повторная строка не объединяется, не суммируется и не отбрасывается. Вместо
публикации противоречивого набора возвращается `sales_page_overlap`.

Миграция `036_sales_page_restarts.sql` добавляет отдельный счётчик повторных
загрузок. Для действующего задания Sales разрешены **два перезапуска всей
цепочки**, то есть не более трёх полных попыток. При перезапуске удаляются
только временные страницы этого задания, очищаются времена наблюдения и
число страниц. Кабинет, период, cutoff, общий срок задания и ограничения
запросов сохраняются. Новая попытка начинается не раньше чем через 65 секунд
и не раньше сохранённого ограничения источника. Ozon использует транспорт
без интерактивного кеша, поэтому повтор получает новые ответы.

Счётчик перезапусков не сбрасывается после успешного сохранения очередной
страницы. После исчерпания бюджета задание получает
`sales_page_overlap_exhausted`. Завершённые и уже проваленные задания эта
функция не возобновляет. Старый владелец или истёкшая аренда не могут
перезапустить работу нового владельца. Доступ к функции есть только у роли
сборщика; MCP остаётся читателем.

Ozon дополнительно проверяет, что каждая дата ответа входит в запрошенный
период. Нарушение даёт `invalid_sales_response` с обезличенной диагностикой
`date_outside_requested_period`. Оно не считается временным пересечением.

Такая обработка позволяет повторить непоследовательную выгрузку, но сама
по себе не доказывает отсутствие пропущенных строк в изменяемой статистике
поставщика. Для проверки полноты нужны закрытые дни, покрытие и контрольные
итоги. Остальные причины `invalid_source_publication` по-прежнему требуют
собственной диагностики.

## Реклама WB

Fullstats v3 возвращает товары в `days[].apps[].nms`. Обработчик теперь читает
это поле и сохраняет детализацию по SKU. Старое `nm` поддерживается для
совместимости. Одновременное присутствие обоих полей и некорректный массив
отклоняются. Дневной итог не складывается повторно с товарными строками.

Версия checkpoint статистики изменена на `wb_stats_v3_sku`: сохранённый старым
обработчиком итог кампании не выдаётся за новую детализацию по товарам.

Если WB возвращает больше кликов, чем показов, существующая проверка качества
продолжает отклонять такой набор. Теперь причина выделена как
`promotion_counts_inconsistent`. Только для WB Advertising с cutoff текущей
бизнес-даты и в пределах срока задания допускается повтор по существующей
политике пауз и не более восьми последовательных неудачных попыток. Противоречивый ответ не сохраняется
как успешная страница; уже полученные корректные страницы продолжают
использоваться. Для устаревшего cutoff, неизвестной структуры, чужой кампании
или неверного периода ошибка остаётся окончательной. Числа не исправляются
автоматически. При повторяющемся нарушении источник остаётся неполным.

## Чтение истории

Если строки опубликованного дневного снимка выходят за его заявленную дату,
читатель исключает **весь этот снимок**, возвращает для даты
`coverage.state=partial, served=false` и помечает результат `PARTIAL`.
Корректные соседние дни остаются доступны. Если пригодных дней нет, список
строк пуст; нулевая сумма продаж не создаётся.

Нарушение прав доступа, схемы или количества строк по-прежнему приводит к
отказу. Исходные снимки остаются неизменяемыми: восстановление некорректного
дня потребует отдельной проверенной загрузки, а не переноса старых строк
между датами или подстановки другого снимка без явной отметки.

## Проверка и выпуск

Проверки воспроизводят пересечение страниц для обоих маркетплейсов, свежую
публикацию после перезапуска, сохранение паузы, исчерпание бюджета, потерю
аренды, права ролей, повтор противоречивой рекламы, формат `nms` и изоляцию
некорректного дня в реальной одноразовой PostgreSQL-базе. В них используются
синтетические данные и локальные HTTP-заглушки.

Миграция 036 должна применяться до запуска обновлённого сборщика. Готовность
БД и проверка контракта сборщика проверяют наличие функции и её права.
После выпуска нужно проверить оба плановых среза по всем кабинетам:
публикацию Sales/Advertising, ошибки, покрытие дат и контрольные итоги.
Успешные тесты кода не подтверждают восстановление исторических данных или
работоспособность ещё не обновлённого продакшена.

### Операторский повтор преждевременно завершённого advertising job

Миграция `040_wb_advertising_collection_recovery.sql` добавляет
`daily_reporting.resume_failed_wb_advertising`. Функция не вызывает WB и
доступна только администратору. Она возвращает в очередь только конкретное
задание WB advertising с ошибкой `promotion_counts_inconsistent`, одной
использованной попыткой, cutoff текущей бизнес-даты и ещё действующим
24-часовым сроком. Старый ответ не объявляется корректным. В audit остаются
исходная ошибка, generation задания, оператор и причина. Использованная попытка
сохраняется в лимите восьми; повтор функции для того же job запрещён.

```sql
SELECT daily_reporting.resume_failed_wb_advertising(
    $1, $2, $3, $4, $5
);
```

Параметры: ожидаемый account ID, job ID, generation, точный cutoff и ссылка на
исправление. Сначала проверить, что установлен исправленный collector и что
нет опубликованного snapshot того же cutoff. После вызова дождаться обычного
сборщика и проверить `source_snapshots` и completeness. Если WB продолжит
возвращать больше кликов, чем показов, задание снова завершится ошибкой;
искажать показатели или публиковать противоречивый ответ нельзя.
